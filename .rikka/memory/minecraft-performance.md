- Rule for all of them: no settings or toggles, identical game results (RNG order, iteration order, packet order) and an identical image. Nothing may ship data generated from one Minecraft version, and a hook copies a vanilla method body only when it is a core frame-time win; everything else is a narrow `@Redirect`/`@WrapOperation` that fails loudly when its target changes. Each area has its own mixin config next to `rikka.mixins.json`, listed in `fabric.mod.json`, with mixins in `sh.rikka.client.mixin.<area>`.
- `memory` (`rikka.memory.mixins.json`): `PalettedContainer.threadingDetector` holds shared `FREE`/`HELD` tokens and gets a real `ThreadingDetector` only on contention; `ZeroBitStorage` is shared per size; eager DFU optimization of `LEVEL_SUMMARY` is skipped.
- `startup` (same config, started from `Main.main`): `ClassPreloader` + `ClassLoadJournal` record every loaded class by turning on the JVM's `class+load` log into `<gameDir>/rikka/startup/classes.log` (DiagnosticCommand MBean `vmLog`), and on the next launch three threads load and link the previous session's names without initializing them. No list ships; names that no longer load are skipped, and preloaded names re-enter the new log, so the set follows updates by itself. `ServerKeyPairs` generates the integrated server's RSA key ahead.
- `simulation` (`rikka.simulation.mixins.json`): `LayerLightSectionStorage.swapSectionMap` publishes a persistent `LightSectionSnapshot` instead of cloning the section map per light batch; `PalettedContainer.pack`/`unpack`/`count` use thread-local scratch and an id histogram.
- `simulation/packet`: `ChunkPacketPacer` stops the client's `PacketProcessor` drain before the next `ClientboundLevelChunkWithLightPacket` once chunk handling used half of the smoothed frame period (at least 0.25 ms); order is never changed, later packets simply wait for the next frame. Only `Minecraft.runTick`'s drain is paced; server processors drain fully. The server's chunk batch size is measured on the network thread and is unaffected.
- `simulation/thread`: `WorkerPriority` raises the niceness of each `Worker-Main` thread by 5 at its first compile task through `getpriority`/`setpriority` (FFM), because HotSpot ignores Java priorities on Linux; other platforms apply vanilla's priorities themselves.
- `render/entity` (`rikka.entity.mixins.json`): `ModelPart.render` is overwritten by `ModelPartRenderer` over per-cube `CubeMesh` data; `BufferBuilder` gains `putBakedQuad` through `BakedQuadWriter`. Both write whole vertices straight into the builder (`QuadVertexSink`) only when `EntityVertexLayout` equals `DefaultVertexFormat.ENTITY` and the builder is a `QUADS` builder of that format; otherwise vanilla code runs. Positions and normals replicate JOML's operation order (`Math.fma` chains, identity/translation branches) so vertex bytes equal vanilla's; check any change byte for byte against the vanilla routine, since stills miss bit drift.
- `RenderTypeGroupMixin` memoizes `RenderTypeFeatureRenderer.Group.getOrAddDraw` per `RenderType` instance for reorderable groups, skipping `RenderType.prepare()` and the deep-equality draw search on every render-type switch. `StagedVertexBuffer` copies its slices in 128 KiB chunks on the render thread plus two `Rikka Vertex Copy` threads, flushed before the first `freeVertexData`.
- `PalettedContainer` and `Minecraft` are mixed into by several configs; their injection points do not overlap.
- Known unaddressed costs: geared humanoids are bound by vertex volume (items and armor re-transformed on the CPU each frame), `ClientLevel.animateTick` is about a third of the client tick, `DistanceManager`/`ChunkTracker` on the server thread, shaderc compilation on reload.
