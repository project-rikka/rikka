---
title: Windows executables, DLLs and the portable Windows ZIPs
description: rikka_application/rikka_native_library embed version resources; windows_zip packs apps, the SDK and mod natives.
about: bazel/windows
tags: [windows, release]
---

- `//bazel/windows:defs.bzl` `rikka_application(name, product, …)` wraps `rikka_binary`; every app under `apps/general` uses it. `rikka_native_library(name, product, soname, …)` wraps `rikka_shared_library` for C-ABI DLLs (`//sdk/native:rikka`). On Windows both link `<file>.res.o` (`windows_resource`: llvm-mingw `windres` over `resource.rc.in`, plus `application.manifest.in` for executables) through `compile_data` + `-Clink-arg=$(location)`; Linux builds are unchanged.
- Executables get RT_MANIFEST id 1 (PerMonitorV2 + `true/pm`, UTF-8 code page, long paths, Common Controls 6, Windows 10/11 supportedOS, asInvoker) and VERSIONINFO (FILETYPE 1); DLLs get only VERSIONINFO (FILETYPE 2). Nothing carries an icon. The version comes from the string flag `--//bazel/windows:version` (default 0.1.0).
- `rikka_shared_library` on Windows passes `--out-implib=$(BINDIR)/<pkg>/<crate>.dll.lib`, the name rules_rust expects for a cdylib's interface library; lld writes a COFF short-import archive MSVC and MinGW both read.
- `windows_zip` has an incoming transition to `//bazel/platforms:windows`, so it builds from any configuration (the Minecraft mod embeds one). It runs `//xtask/windows/package:windows-package`: `program` at the root, `libraries` (target → folder) with each `.dll` in its folder, `import_libraries` (target → entry of its `.dll.lib`), `files` (target → entry), `packages` (filegroup → folder, keeping paths within the package), and always Rikka's LICENSE and THIRD_PARTY notices (`licenses/rikka/`, implicit attr, so those files are visible to `//bazel/windows`). Runtime DLLs a binary reaches land in that binary's folder, their licences in `licenses/`. Entries are sorted, case-insensitively unique, dated 1980-01-01, deflated.
- `rikka_application` declares `<name>_windows_zip` (manual, flat: exe and DLLs at the root). There is no `share/`: Windows programs carry their UI and icon fonts compiled in (`rikka-embedded-fonts`), and `rikka-shipped` resolves `installed` paths beside the exe or beside the DLL holding the code.
- The binaries import no runtime DLL: FFmpeg and Slang are dlopened (rikka-ffmpeg finds its DLLs beside the exe or DLL through rikka-shipped and loads them with `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR`). A library that loads or embeds part of `NIX["windows_runtime"]` lists a `windows_runtime(libraries, licenses, icon_font_licenses)` target in its Windows `data` (`rikka-ffmpeg`, `rikka-slang`, `rikka-embedded-fonts`); an aspect over `deps`/`data` collects `WindowsRuntimeInfo` (`libraries`, `files`, `trees`) per binary. Only Animate ships Slang. Tree-sitter grammar DLLs are not built for Windows yet, so syntax highlighting is absent there.
- The packer fails when the program is not at the root or any packed .exe/.dll imports (`objdump -p`) a DLL that is neither in its own folder nor a Windows system DLL (`xtask/windows/package/src/system.rs`, api-ms-win-*/ext-ms-win-* api sets); add genuine system DLLs there.
- Build: `bazel run //xtask -- dist windows --version x.y.z --out <dir>` (= `--config=windows --config=release --//bazel/windows:version=…`) writes `rikka-<id>-<version>-windows-x86_64.zip` per component with `windows` set (apps and `sdk`); `xtask release` uploads them to the version's GitHub release.
- The cc toolchain for Windows has no `.exe` artifact names, so `rikka_cc_binary`/`rikka_cc_test` are Linux-only; Windows C/C++ consumers use the SDK ZIP.
- Windows main.rs files carry `#![cfg_attr(windows, windows_subsystem = "windows")]`. Linux-only trees (system, apps/system, compositor, daemons, nix and Linux-API crates elsewhere) carry `target_compatible_with = ["@platforms//os:linux"]` so `--config=windows //...` skips them.
