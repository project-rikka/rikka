---
title: Test layout and shared test helpers
description: Where tests live, the rikka-test-* helper crates, machine tests, time limits and deliberately untested seams.
tags: [testing]
---

- Layout: `tests/main.rs` declares topic modules (`tests/<topic>.rs` or `tests/<topic>/`) and one `support` or `common` module; `tests/machine.rs` may declare the same support module.
- Helper crates, `testonly` so only tests use them: `rikka-test-renderer` (2D, over rikka-renderer only: serialized `TestRenderer`, `lock_gpu`, `renderer`, `video_renderer`, `streaming_renderer`, `compute_renderer`, `renderer_3d`, `fluid_renderer`, `ray_renderer` (device feature sets), `init_tracing` — a WARN tracing subscriber every `*_renderer` installs, so renderer warnings and validation messages reach the test's output; tests building `Renderer::new(&Gpu::builder()…build()?)` themselves call it first; compute-only suites (physics, image-edit headless) build a bare `rikka_gpu::Gpu` and keep only its `Compute`), `rikka-test-renderer-3d` (`sphere`, `standard`, `minimal_look` with every effect and illumination off, `built(template, draw)` redrawing until a runtime template's optimized build is `Built`; the only helper that depends on rikka-renderer-3d), `rikka-test-display` (below), `rikka-test-seam` (`Host` running a `Seam` on a thread), `rikka-test-llm` (`Scripted` and `Server`: a local HTTP server speaking real wire protocols, so `Provider` stays private), `rikka-test-mcp` (`echo_server(folder)`: a stdio MCP server script with tools, prompts, completions and resources), `rikka-test-bus` (below), `rikka-test-keyring`, `rikka-test-fonts`, `rikka-test-fido` (fake CTAP keys), `rikka-test-nixfmt`, `rikka-test-certificate-transparency` (Chrome-signed CT log list fixture, `Signer`, `LogListServer`, `serving`), `rikka-test-proton` (the one fake Proton HTTP server `serve`/`Request`/`Response`/`ResponseFuture`/`Record` with `json_response`/`response`/`not_found`/`success`/`delayed`, `api`/`signed_in_api`, `FakeSrp` + `SIGNED_MODULUS`, and the `Owner`/`NodeKey`/`HashKey` key fixtures; visible to apps' tests) and `rikka-test-proton-drive` (the one stateful `DummyDrive` over it, configured by `Shape`: seeded fixture tree, corruption, conflicts, failing uploads, sharing and photo routes; used by drive and drive-sync tests).
- Mesh helpers: `rikka-test-meshes` (corpus, sample patches, seeded selections, `sweep_edit`/`sweep_chains`/`Sweep`) and the app-private `modeler-test-sweep` (`OperatorSweep` over registered operators with undo/redo checks); see the mesh-robustness-sweeps note.
- Programs (shell, apps' root packages, xtask) have almost no tests; their testable logic belongs in app-private crates.
- `bazel test` runs every test target through its hermetic launcher (see the bazel-build note): one process and one fresh scratch home/XDG/runtime tree per test, `limit` seconds each (60 by default), four at once within a shard, spread over Bazel shards, remotely unless tagged; so tests must not share fixed paths, ports or socket names outside that tree. `gpu = True` suites (renderer, widgets, ui, physics GPU crates, paint-document, cut-render, …) run only with `--config=gpu`, locally, at most 4 suites at once and one test at a time; rikka-physics-cloth is `shared = True` (one process per binary, 300 s). The raw test binary is `<name>_bin`; target `<name>` with `--test_arg=<filter>` is how to run a subset.
- NVIDIA's Vulkan ICD fails `vkCreateInstance` when a process without an X display destroys its instance and creates another, so suites that make a device per test thread pass only one process per test; never mark rikka-renderer, rikka-renderer-3d or paint-document `shared = True`.
- A test that needs a child process the code under test spawned learns it from the child itself (rikka-web's fake engine writes its pid and channel fd into a FIFO the test opened before starting the runtime), never by scanning `/proc`, whose `environ` reads empty while the child is in `execve`.
- Machine tests exist in rikka-renderer, rikka-renderer-3d, rikka-widgets, rikka-compositor-surface, rikka-compositor-input, rikka-compositor-kms and rikka-compositor (both need vkms, see the multi-GPU note), rikka-audio, rikka-hifi, rikka-video (dmabuf → Vulkan Video coding), music-stream, rikka-physics-cloth, cut-render, discord-voice, browser-reader, browser-translate and rikka-web (the last three need the installed rikka-gecko). Plain `bazel test` leaves them out; `bazel test --config=machine <targets>` runs them locally and `exclusive` (they share sound cards) with the real `XDG_RUNTIME_DIR`, so PipeWire and the session bus are reachable.
- Each test has 60 s (`rikka_test(limit = …)`); the launcher names a test that timed out.
- rikka-physics-cloth's `support/` is split into `device.rs` (one shared device, kernels kept alive), `scene.rs` (`style`, `sheet_asset`), `sheet.rs`, `measure.rs` and `sample.rs`; `machine.rs` declares an inline `mod support` with only `device`, `scene` and `sample`, so neither binary needs dead-code allows. The device for the binary and keeps one `Cloth` alive so its kernels survive between tests; tests still take turns through a thread-local guard. The stop-and-read dance scenario is one test (`replay/pacing.rs`) because it is the costliest simulation.
- A wall-clock wait inside a renderer test (resting) drops its `GpuLock` while it sleeps and takes `rikka_test_renderer::lock_gpu()` again.
- Tests that set environment variables run alone in their binary or behind a lock, since a shared-process suite runs every topic in one process.
- Kept in step by hand, untested: curve vs atlas glyph crossover.
- `rikka-test-display` (crates/compositor) is the threaded display harness of the compositor protocol crates and of `rikka-wayland-client`'s tests: `Display::<S>::start(|reactor, notes| state)` runs a state implementing `Host` (`display_handle()`) on the `rikka-test-display` thread, `call(|state| ..)` runs a task there, `connect(ClientOptions)` hands back the client socket, `expect(fragment)` waits for a `Notes::note` line (disconnect reasons are noted for free). `Client::<R>::connect(stream, |queue| ..)` (or `connect_to(socket path, ..)`) is the shared client half over the in-house `rikka-wayland-client`, also used by rikka-compositor's `tests/common` and its `frame_cost` bench (registry kept by a tap, so bind through `global::<P>(version)` (capped at the advertised version) or `bind(name, version)`, never `registry().bind`; `globals`, `advertises`, `roundtrip`, `until(what, done)` with `with_patience`, `fails`, `protocol_error`); `Canvas::new(&wl_shm, w, h, format)` (or `client.canvas(w, h, format)`) is a 32-bit memfd shm buffer with public `buffer`, `pool` and `memory` (`fill`, `paint`, `paint_each`, `read`), the only shm helper of every compositor test suite and `dispatch_until`/`dispatch_next`/`wait_readable` wait on the socket and extra fds. Each crate's `tests/common` keeps only its `State`, a `Server` newtype that derefs to `Display<State>` and a `Wayland` newtype over `Client<Received>`; rikka-compositor-server keeps its own server harness.
- `rikka-test-bus`: `PrivateBus::start()` writes its own session config into the test's temp dir, starts `dbus-daemon` with it and sets `DBUS_SESSION_BUS_ADDRESS` (`stand_in_for_system_bus` also sets the system address); `TIMEOUT` bounds waits. Bus and keyring tests therefore run on the remote executors like any other; `start()` returns `None` (and the test returns early) only when `dbus-daemon` fails to start. Tests wait on channels or signal streams, never by polling. Tests that touch secrets use `rikka-test-keyring` (`TestKeyring::unlocked()`, one per test process). Tests that talk to the real system bus (some rikka-compositor tests) are never result-cached.
- `rikka-test-objects` (crates/daemons) is a scriptable fake D-Bus ObjectManager service on the private bus (`FakeService`; daemon-integration note); NetworkManager-style tests build their fake daemon from it.
- rikka-compositor's `tests/common::Harness` runs a headless compositor with scratch runtime, config and state dirs; `Harness::supervising(extent, script)` puts a fake `rikka-shell` script first on PATH and starts it as the desktop (`tests/desktop.rs`). Snapshot probes must avoid the themed cursor at (0,0) (a black arrow), `Harness::full` display corners and every window's rounded corners and 1 px edge (floating windows cascade from (48,48); tiles sit 8 px in).
- Process-exit safety is tested by rikka-renderer-3d's `three::exit`: the test re-runs its own binary (env `RIKKA_RENDERER_3D_EXIT_CHILD`) as children that return with a slang draft, an `-O2` optimization or a leaked renderer's pipelines in flight, and asserts each exits cleanly. Children run one at a time: a drafting child peaks at ~2.2 GB, and 30+ at once got OOM-killed. Exit crashes are timing-sensitive (a draft is in IR lowering 200–800 ms in), so the drafting children exit at fixed delays after the compiler opened.
