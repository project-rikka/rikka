title: GPU queues, submits and pipeline compilation (rikka-gpu)
description: Queue families on declared need, transfer lane, global priority, submits, background pipelines, pass timing.
about: crates/graphics/rikka-gpu
tags: [renderer, vulkan]

- Queues are created only on declared need, since each costs pinned driver memory (NVIDIA, measured: ~2 MiB VRAM and 1.5–3 MB host-visible each; a bare VkDevice is ~11.6 MB host-visible plus driver threads `[vkrt]`, `[vkps]` and an unnamed ~100 Hz one that every NVIDIA Vulkan process has). `GpuBuilder::video_decode()` / `video_encode()` add one Vulkan Video family each; FFmpeg does its compute/transfer on the graphics family under the graphics `QueueLock`. Without them `video_device()` is `None` and video is coded in software. `background_compute()` (rikka-app `App::computes_in_background()`: Animate and Paint) adds the async compute queue.
- `GpuBuilder::upload_queue()` adds a transfer-only queue family (granularity 1×1) when the device has one (`core/transfer.rs`, `TransferLane`): drm textures are then CONCURRENT across graphics+transfer, `Renderer::take_uploads` (every `textures()` guard drop) submits staged-only, single-level textures there at once (waiting on the last submitted frame), and a frame waits on the transfer timeline only for textures it samples (`TexturePool::take_over` → `GpuFrameCtx::waits_while_sampling`, added to both setup and canvas batches) or writes. Destroyed/grown images outlive their transfer through `DeferredDrop::drop_after`. Transfer spans log as pass `rikka.transfer`; mipped or mixed-fill textures stay on the graphics path.
- `GpuBuilder::latency_critical()` requests global priority HIGH for the graphics queues and falls back with an info log when the driver refuses (NVIDIA needs CAP_SYS_NICE on the creating thread). Global priority applies per queue family, so with it the background compute lane only takes its own compute family, never a graphics-family queue.
- All queue submits go through `RenderDevice::submit(QueueRole, ..)`, which takes the queue's lock.
- Pipelines compile in the background through `core::pipeline::Compiling<T>` on up to four `rikka-pipelines-N` threads (`core/background.rs`: `Pool` runs jobs inline when no thread starts, `Slot` is the queued → running → done state both `Compiling` and `Provision` wait on), started at construction or when a material, effect or viewport is created. fx pipelines (`fx/pipelines.rs`) start compiling with the renderer, so a first fade or backdrop finds them built; a pipeline needed before it is built is built inline. The pipeline cache persists in `$XDG_CACHE_HOME/rikka/renderer/` when it grew: on `Renderer::trim()` → `Gpu::trim()` (queued to the pipelines thread), when the device drops, and on demand through `Gpu::save_pipeline_cache()`; never on a timer while frames run. Big types keep their impls split by job inside a module directory (`compute/batch/`, `texture/pool/`, `fx/executor/`, `core/device/`, `draw/batcher/`, `draw/primitive_pipeline/`).
- Shutdown of the process-wide pools (`rikka-pipelines-N`, `rikka-provision`): owners cancel or wait on drop (`Compiling`/`Provision` drop claims the slot: a queued job is marked taken and never builds, a running one is waited for), and every job runs through `core/exit.rs`, whose `atexit` drain (registered when a pool starts and again after the first job, since NVIDIA's compiler library registers its destructors lazily during the first pipeline build) stops jobs from starting and waits for running ones, so a leaked or static `Gpu` never builds pipelines while `exit()` tears the driver down. Per-owner threads (`rikka-reaper`, `rikka-glyphs`, `rikka-compute-completion`, `rikka-scanout-wait`) are joined by their owners' `Drop`.
- `ctx.begin_pass(name)`/`end_pass()` nest debug labels (per-frame pass and stamp vectors are reserved for `TIMED_PASSES`, so timing never allocates) and timestamp queries; timings (each with its `frame` value, plus a whole-frame `rikka.frame` span) are logged at debug under the `rikka_renderer::passes` tracing target. `benchmarks/render` (`bazel run --config=bench //benchmarks/render:gpu -- [--hz=N --frames=N] [name…]`) captures them for client and compositor-shaped scenes; NVIDIA swings between P8 and P0 under paced load, so compare builds unpaced (`--hz=100000`) or in alternating runs. Its `Counting` allocator counts every thread during a measured render and records backtraces (with thread names) of the first 8 steady-frame allocations; the steady-allocation assertion prints them.
