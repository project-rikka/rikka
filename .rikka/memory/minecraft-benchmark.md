- `benchmarks/minecraft` is a testonly Fabric mod (`rikka-bench`, `sh.rikka.bench`) plus clients `//benchmarks/minecraft:vanilla` (game + bench) and `:rikka` (game + bench + `//minecraft:rikka`). It runs in `benchmarks/minecraft/run` (gitignored); `RIKKA_MINECRAFT_RUN=<dir>` moves any `minecraft_client` run directory.
- Run: `RIKKA_BENCH_LABEL=<label> [RIKKA_BENCH_REFERENCE=<label>] [RIKKA_BENCH_SCENES=a,b] [RIKKA_BENCH_PRESET=fancy|fast|fabulous] bazel run //benchmarks/minecraft:rikka -- --width 1920 --height 1080`. It writes `options.txt`, creates or opens the fixed-seed world `bench`, runs the script and exits; results are `run/bench/<label>/report.json` and PNG stills.
- Stills (`overview`, `street`, `down`, `crowd`, `wardrobe`) are taken with ticks frozen, texture animation and lightmap flicker held, game time pinned, glint scrolling off, HUD hidden, so vanilla and an unchanged client match exactly; `difference.differing_pixels` compares against the reference label. Expect a few dozen differing pixels on `down`/`street` from depth ties; thousands mean a real bug. Use the same scene list for reference and candidate, since load order changes tie pixels.
- `wardrobe` (`Wardrobe`, built with commands) lines up armor stands, mobs, item displays and block entities that cover dyed, trimmed and enchanted armor, special item models, eyes, energy swirl, translucent layers and sprite-mapped models; a few hundred of its pixels vary between runs. `hand` and `inventory` put the player in survival among them with a filled hotbar and armor, HUD shown: first-person hand, hotbar icons and the inventory's player model. Those two are for looking at, not for pixel counts (random offline skin, hand sway).
- `vault` (still and hover flight, `Vault`) is a sealed stone box holding 280 mobs and block entities with a one-block window, beside visible mobs and chests: the occlusion-culling case.
- `RIKKA_BENCH_BOOST` drives the Boost mod through a pre-launch edit of the run directory's profile: unset disables the mod, set (even empty) enables it with its default toggles, and comma-separated `key=value` pairs override settings by id (`render_scale=true,render_scale_value=0.75`).
- Never start two games on one run directory (the profile edit and the world lock race); a second game on the machine also distorts every timing.
- Flights move the spectator on a tick-indexed path: `orbit_cold`, `orbit_warm`, `spin`, `cruise` (40 blocks/s, chunk loading), `crowd` (380 mobs), `gear` (380 armor stands in enchanted armor with sword and shield, the PvP-like case) and `arrive` (teleport 1600 blocks into pre-generated terrain, recorded from the first tick). They report fps, 1%/0.1% lows, frame percentiles, `stall_ms_per_second` (time above twice the median), tick cost, render-thread CPU ms per frame, waits in acquire/submit/present, `run_queue_ms_per_second` (render thread runnable but not running, from `/proc/thread-self/schedstat`), median GPU ms per span, allocation per frame and GC counts.
- With a JFR recording running, every frame is a `sh.rikka.bench.Frame` event (flight, ticks, CPU, allocation, waits, run-queue time), so `jdk.CPUTimeSample`, `jdk.ClassLoad` and GC events can be joined to slow frames with the `jdk.jfr.consumer` API. Start one with `JAVA_TOOL_OPTIONS=-XX:StartFlightRecording=filename=<file>,settings=profile,jdk.CPUTimeSample#enabled=true,jdk.ClassLoad#enabled=true`. The render thread is named `main` there.
- Noise on the isolated screen: its compositors take the GPU for about 1 ms each refresh (a 1.6 ms frame every 8 to 16 ms, visible as a long submit wait), and other jobs on the machine show up as run-queue time. Compare CPU ms, GPU medians and worst frames with their waits rather than raw fps lows.
- Baseline on RTX 4060 / i5-12400 at 1080p fancy: vanilla `orbit_warm` about 965 fps (CPU 0.37 ms, GPU 0.55 ms), `crowd` about 300 fps.
