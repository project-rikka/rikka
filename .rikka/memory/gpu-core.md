- `rikka-gpu` is the layer under `rikka-renderer` (2D) and `rikka-renderer-3d`: Vulkan 1.3, dynamic rendering, synchronization2, timeline semaphores, descriptor indexing. It re-exports `ash`. It has no scene, text or 3D code and does not depend on `rikka-text`, `rikka-slang` or `glam`.
- Apps use its flat facade for data types: `Compute`, `ComputeBuffer`, `ComputeImage`, `Ticket`, `ComputedFrame`, `Kernel`, `Pixels`, `Rows`, `TextureId`, `TextureFormat`, `Uploads`, `Filtering`, `DmabufSpec`, `ExportedDmabuf`, `SharedRows`, `VideoDeviceHandles`, `Reclaimer`, `Error`. `rikka-renderer` re-exports only the ones its own signatures name.
- The renderers reach internals through `#[doc(hidden)] pub mod` trees (`core`, `compute`, `texture`, `drm`, `video`, `reclaim`, `error`, `identity`, `pixels`): `core::runtime::GpuRuntime`, `texture::TexturePool`, `core::device::RenderDevice`. Only `rikka-renderer` and `rikka-renderer-3d` use those paths.
- A device is a `Gpu` (`src/gpu.rs`, `Clone + Send + Sync`, one `Arc`) made by `Gpu::builder()` (`GpuBuilder`: `app_name`, `validation`, `drm_node`, `with_3d`, `compute_support`, `background_compute`, `video_decode`/`video_encode`, `latency_critical`, `upload_queue`, `ray_tracing`); `rikka_renderer::Renderer::new(&gpu)` draws on it and `renderer.gpu()` hands it back. It owns the device-level queries (`vendor_id`, `drm_nodes`, `traces_rays`, cached `dmabuf_render_formats`/`dmabuf_texture_formats`/`dmabuf_export_formats`, `video_device`, `save_pipeline_cache`, `trim`) and the lazily created `Compute`, so compute and video consumers (rikka-image-edit, the physics solvers, rikka-dmabuf-convert, rikka-video, rikka-vulkan-video, rikka-capture, rikka-record, replay, remote, discord-stream) take `&Gpu` or `Compute` and do not depend on rikka-renderer. Validation layers follow the `//crates/graphics/rikka-gpu:validation` flag. The request (`core/device/request.rs` `DeviceRequest { drm_node, three_d, compute, video, transfer, ray_tracing, … }`) decides features and queues. `three_d` turns on the features the 3D crate needs; `RenderDevice::three_d()` reports it. There is no WSI: no surface or swapchain extension is requested and there is no present queue.
- Reclaim: `Reclaimer` (`Clone + Send + Sync`) queues `ReclaimRequest::{Texture, Target, Buffer, Gpu(Box<dyn Any + Send>), Routed(Box<dyn Any + Send>)}`. `Reclaimer::route(value)` sends a typed request an upper crate downcasts: `rikka-renderer` takes its glyph and instance stores, everything else goes to the renderer's extension.
- Shaders: `shaders/` (crate `shaders_gpu`) holds `fullscreen.slang` (the vertex stage of every full-screen pass in all three crates) and `ycbcr_convert.slang`.
- SPIR-V is validated where it is made, not where it is loaded: every `rikka_shaders` object, built-in template and effect program is compiled with `SLANG_RUN_SPIRV_VALIDATION=1`, so libslang's SPIRV-Tools refuses invalid modules at build time (it checks the module before optimisation: a helper taking a workgroup pointer needs `[ForceInline]`). Loading only takes build-time `rikka_spirv::Shader`s (every `rikka_shaders` package and the 3D programs; `Compute::kernel(Shader)` keys kernels by their build-time hash, `BackdropShader::new(Shader)`), so no built-in shader is parsed or hashed at run time, or libslang's own run-time output, which rikka-renderer-3d reflects with `rikka_spirv::reflect` and checks (stage, capability allowlist, table bindings) in `src/shader.rs`, refusing with `Error::InvalidShader`.
- Tracing targets keep the `rikka_renderer::` prefix (`rikka_renderer::passes`, `::imports`, `::memory`, `::vulkan`, `::graph`), since benchmarks and the compositor filter on them.
- Errors (`rikka_gpu::Error`): `Unsupported`, `Invalid` (caller mistakes, with a message), `Unknown(Resource::Texture)`, `NotEnabled(Capability::{ThreeD, Compute, RayTracing})`, `Full(Store)`, `Unsettled` (a `Present` stayed stale), `ScanoutWaiter`, driver and allocation causes.
- Code map: `core/{instance,device/,runtime,frame,frame_ctx,memory,staging,provision,pipeline,pipeline_cache,background,resource_table,sampler,convert,transfer,retire,barrier,caps}`, `core/image/{access,recording,desc,gpu,mips}` (image access states, provisional layout tracking, descriptions, `GpuImage`, mip chains), `compute/`, `texture/`, `drm/` (Linux), `win32/` (Windows), `video/`.
- Platforms: everything dmabuf/DRM/sync-file (`drm/`, `core/dmabuf_support`, `DrmNodeIds`, `GpuBuilder::drm_node`, `Gpu::drm_nodes`/`dmabuf_*_formats`, dmabuf texture and compute imports, sync-file waits) is `#[cfg(unix)]`; the device keeps it in `core::device::Interop`, whose Windows form holds `Win32Device` (surface, win32_surface and swapchain loaders) when the graphics family can present. `win32/` holds `Surface` and `Swapchain` for rikka-swapchain (swapchain-presenter note) and DXGI adapter ranking: the adapter DXGI ranks first for `DXGI_GPU_PREFERENCE_HIGH_PERFORMANCE` gets +1000 score. `BufferId::External` names any externally owned destination buffer. DRM-layout row uploads (`create_drm`, colour lookups) and the colour fourcc table (`texture/packed.rs`) stay cross-platform.
- Topics live in their own notes: queues and pipelines (gpu-queues), memory and frame slots (gpu-memory), textures and uploads (gpu-textures), compute (gpu-compute).
