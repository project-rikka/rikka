---
title: Compositor backends and frame loop
description: rikka-compositor's DRM/nested/headless backends, event-driven pacing, fences, glass damage and GPU limits.
about: system/rikka-compositor
tags: [compositor, rendering]
---

- Rikka's own Wayland stack (`crates/foundation` scanner and wire, `crates/compositor` reactor, server, surface, seat, shell, output, selection, desktop, kms, input, xwm) handles protocols and state; `src/` is wiring and policy. `rikka-renderer` renders directly.
- Backends (`src/backend`): `kms` when no display exists, `nested` inside a Wayland session, `--headless[=WxH] [--socket name]` for offscreen simple sessions (ADE's agent desktop).
- `backend/nested/` is a `rikka-wayland` client of the host compositor: `window.rs` (xdg-toplevel titled with the socket, app id `rikka-compositor`, fractional scale, entered outputs), `screens.rs` (host `wl_output` scale and refresh), `host.rs` (the queue state and handlers), `input.rs` (`rikka-seat` `DeviceEvent`s → the compositor's pending input), `shortcuts.rs` (`zwp_keyboard_shortcuts_inhibit` on every host seat, so Super chords reach the nested session). It needs a Wayland host with `zwp_linux_dmabuf_v1` ≥ 4 (`Error::Present` names the missing global otherwise); X11 hosts are not supported.
- The nested backend reads the host socket on the state thread (one reactor watch; `rikka_wayland::Host::read_by_owner` for the presenter) and presents with `rikka_present::Presenter` (exported dmabufs, explicit sync when the host has it). A frame is drawn when wanted and no host frame callback is outstanding; `wp_presentation` feedback, keyed by frame number, completes `presented` (a discarded one ends in `refreshed`). A host resize, scale or refresh change re-describes the one head `nested-0`, so the window size is the output mode; the configured transform is drawn by the presenter (`Presenter::set_transform`) and undone for pointer positions.
- Nested input: the host cursor is hidden over the window; pointer positions map through the output's configured scale and transform; relative motion rides with the next absolute motion; host key repeats are dropped (the nested seat repeats itself with its own keymap); touch arrives as rikka-seat's primary-button emulation. `HostInput` tracks keys and buttons it delivered: losing host keyboard focus releases every held key and leaving the window releases held buttons.
- Threads: state (main reactor, all client IO and policy), `rikka-input` (libinput, shared pointer position, cursor fast path) and one `rikka-kms-<minor>` commit thread per GPU (SCHED_FIFO via RealtimeKit). The state thread asks for `nice -10` and stays `SCHED_OTHER`.
- `rikka-input` hands events to the state thread through `rikka_compositor_input::InputQueue` (a double buffer behind one eventfd that rings only when re-armed by a drain); configuration reports and failures travel as `InputNotice`s over a reactor mailbox.
- KMS: libseat, udev, GBM, atomic commits and direct Vulkan dmabuf rendering. Every card on the seat drives its displays; one GPU renders (see the multi-GPU note). Cursor moves commit the cursor plane alone on the KMS thread, independent of content frames.
- The state loop is event-driven. Undamaged outputs sleep. Commit blockers (FIFO, commit timing) request the frame they need.
- Every backend frame turn must end in `refreshed` (it clears FIFO barriers and commit-timing waits): through `presented`, or at once when a turn commits nothing and no frame is in flight.
- KMS frames start before vblank from a render journal (`rikka-compositor-kms/src/pacing/`: 500 ms mean + 2× a spread that takes overshoots at once and fades over 6 s, samples capped at two refreshes) of CPU cost and of start-to-GPU-completion time (`render/timeline.rs` stamps each finished renderer frame, `Screen::rendered` feeds `FramePacer::rendered`), lateness and misses; the commit lead uses the same journal. The `frame timeline` report's `rendered_late` counts composited frames whose GPU work ended after their commit deadline. VRR, tearing and stale-timeline outputs render immediately; the per-display VRR policy and the fullscreen content type choose VRR and pacing each frame (see the direct scan-out note).
- The KMS backend asks the root `rikka-boost` service to hold NVIDIA clock floors on input and while animations run (see the GPU boost note). In headless `frame_cost` bench runs nothing is boosted, so cold cycles show P8/P5 costs; `app-maximize` with a freshly built app measures client damage too.
- `bazel run --config=bench //system/rikka-compositor:frame_cost -- [--solid] [scenario…]` measures headless composition on the local GPU (CPU turn and its compose share, the compositor thread's whole CPU time per drawn frame including commit-time uploads (`thread/frame`), GPU per pass incl. `rikka.transfer`, painted area, nvidia-smi clocks and VRAM start/peak/end, dmabufs the compositor imported); scenarios run in the order named (name substrings select; `resize` also selects every `*-resize`), and `FRAME_COST_LOG=<filter>` adds a stderr log. `corners` repaints two small far-apart shm rects per commit (sparse damage). `own-redraw`, `own-resize`, `own-slow-resize` drive a GPU client window through `rikka_present::Presenter` (bucketed buffers while resizing, an exact one after release) and report presents, configures and configure-to-present time. Probe events are taken from the compositor thread only. The GPU is shared, so alternate A/B runs and read the clock column; for A/B binaries copy `.bazel/bin/system/rikka-compositor/frame_cost` between builds.
- The bench's headless display runs at 180 Hz (`Launch::headless_at(extent, millihertz)`; `--headless` stays 60 Hz). `overview` (`measure/overview.rs`) opens four more glass windows, a full-screen frosted overlay layer in the `overview` namespace (windows hidden) and swings 12 window views (cards plus a faded, clipped thumbnail row) open and shut every 60 frames. One-shot scenarios `own-maximize`, `own-slow-maximize` (client answers after 30 ms), `own-restore`, `own-snap` (Super-drag to the left edge), `own-open`, `own-close` repeat 5 cycles after a 3 s rest (GPU back at P8) and print a per-frame timeline per cycle: CPU, ready (start → GPU done, from the headless `gpu_reached` trace), GPU total/draw/blur, fx passes, painted area, emitted, P-state and clocks (nvidia-smi lags ~200 ms), imports/releases and client configure/commit. `--warm` keeps the window redrawing during the rest. `FRAME_COST_APP=<rikka-app binary>` (optionally `FRAME_COST_APP_DATA`, `FRAME_COST_APP_CONFIG` = a folder of `rikka.*.toml`) adds `app-maximize`: the real app toggled by injected Super+M, its stderr kept in `$TMPDIR/frame-cost-app-<pid>.log`.
- The KMS and nested renderers ask for a high-priority GPU queue (`latency_critical`); NVIDIA grants it only with CAP_SYS_NICE. `session/nice.rs` clears the ambient and inheritable capabilities at launch so no child inherits any, and keeps CAP_SYS_NICE effective through renderer and KMS-device creation (renice, queue priority, the KMS thread's direct SCHED_FIFO). Capabilities are per thread: the process keeps CAP_SYS_NICE for its life in every thread made during setup (driver threads); `leave_state_thread` and the KMS thread drop only their own copies so threads they start later hold none. No thread-wide broadcast is attempted, by design.
- Only the KMS thread waits on fences on the CPU; the state thread sees queue waits or reactor sources (the nested backend never waits either: a busy buffer pool retries one refresh later). Busy submission slots postpone the frame.
- Clients: shm buffers keep their own DRM layout (`render/textures.rs` → `Uploads::create_drm`/`stage`, no CPU conversion; `rikka-compositor-pixels` lists the advertised `SHM_FORMATS` and converts to RGBA only for formats the device cannot sample). Damage is uploaded as its disjoint rects (`rikka_compositor_pixels::damaged_rects`; the bounding box when they cover ≥75% of it or exceed 16), copied straight from the pool under the SIGBUS guard. A shown surface uploads at commit (`Scenes::touch` → `ClientTextures::upload_early`, once per composition, so the transfer queue copies before the frame needs it); others upload when composed. All backends build the renderer with `upload_queue()`. Dmabufs are zero-copy and cached, one texture per client buffer (`render/imports.rs`): an import dies as soon as nothing draws it once its wl_buffer is destroyed (`Surfaces::take_destroyed_dmabufs`), else after 3 s idle. `render/tree.rs` swaps a node's texture in place with `repaint_image`, so a client frame costs only its surface damage.
- A buffer format without alpha (XRGB, 10-bit X, YUV) makes `Surface::opaque` the whole surface, for occlusion, fullscreen hiding and scan-out.
- Colour management (see the colour-management note): each surface's description becomes a renderer `ColorId` on its image node (`render/colors.rs`, `Look::Texture(texture, color)`), YUV dmabufs import with the surface's coefficients, range and chroma siting (`DmabufImports` keys include the `Ycbcr`; unset fields keep the BT.601-at-≤576-rows/709, limited, centre guess), single-pixel colours are mapped to sRGB on the CPU, and each KMS screen's `DmabufOutput` carries its blend space. YUYV-style packed YCbCr is not imported.
- Glass panes are read back from each blur region (`rikka-compositor-panes`) by peeling: from the topmost uncovered row, `grow.rs` fits the largest rounded rect that stays inside the region (also one whose top and bottom rows are empty, for circles and capsules), then subtracts it. Panes are rasterized with the client's own `rikka_blur::rectangles`, so both ends agree pixel for pixel. A pane never frosts outside its region; overlapping or touching panes (menus beside cards, submenus) come back as separate rounded rects, a corner hidden under a neighbour borrows its sibling's radius, and at most 16 panes are read.
- Glass: nothing over a pane reports opaque inside its band, and no surface beneath a pane's band goes onto a plane. `glass::repaint` owes a pane every region whose background changed, and all of it when its stack order moved. Its state is settled on every turn, composited or not, so returning from scan-out only damages the frame and keeps every blur.
- `render/tree.rs` declares each surface's largest opaque rect with `opaque_within` and repaints same-texture uploads with `NodeEdit::repaint`, so damage keeps its node.
- A pane whose backdrop changed re-blurs on that frame.
- `glass/placed.rs`: a `Pane` delegates its stale areas to the renderer's `Spread` (lens-aware per region), so a change under a liquid pane re-blurs only what it reaches.
- `render/resting.rs`: every frame turn (`Parts::frames_done`) marks activity; after `rikka_renderer::TRIM_AFTER` without one, a reactor timer calls `Renderer::trim()`, freeing idle blur scratch, spare backdrops and staging.
- Opaque fullscreen hides wallpaper, bars and corner masks. Each KMS frame `rikka_compositor_planes::assign` may put one opaque fullscreen client buffer of mode size on the primary plane (see the direct scan-out note); everything else is composited.
- The shell's IME panel is a small caret-placed layer, so composing only covers what it overlaps.
- `SceneLayers` (`ALL`, `WITHOUT_WINDOWS`) decides what a display draws. A full-size overlay layer in the `rikka_session::surfaces::OVERVIEW` namespace hides all windows; the overview shows them again through window views, which give those windows frames every display frame.
- Drag settlement and heavy bookkeeping run once per frame, never per pointer event.
- Screenshots and recordings go through system memory. Screencast streams and previews use dmabufs. Captures run only when their source changed.
- A whole-output capture without a painted cursor whose buffer matches the output's scene size draws the output composition's own scene with `Viewer::Capture` (`capture/serve.rs` `draw_from_output`, `Scenes::output_captured` holds the client buffers until it finishes); display corners and the composited cursor are `Audience::Only(Viewer::Screen)`. Window captures, painted-cursor captures and other sizes compose their own scene (`compose_capture`).
