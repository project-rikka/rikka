title: Sound playback and capture (rikka-audio)
description: AudioEngine, Track, AudioFeed, AudioCapture sources and fill contract, SoundSender, DeviceWatch and their threads.
about: crates/media/rikka-audio
tags: [media, audio]
---

- Public `rikka-audio` holds the engine, `Track`, capture, device watch, `Pan` and `SoundSender`; decoding is rikka-audio-decode (audio-decode note).
- `AudioEngine` handles `load` (resampled), `stream` (constant memory), whole-sound looping and master volume; there are no effects, loop regions or profiles (Balanced resampling, 512-frame default buffer, 64 voices). `EngineConfig` is builder-only; the public resampling knob is `ResampleQuality`.
- After 2 s with no voice sounding the engine suspends its output stream (`suspend.rs`: `Suspender`, `OutputWaker`); every command and a handle's resume/seek/stop/flush start it again, so idle apps keep no PipeWire stream awake.
- Backends are selected once in `lib.rs`: `pipewire/` (unix) and `wasapi/` (windows), each exporting `OutputHost`, `Output::set_active`, `Resume`/`resume_channel`, `CaptureHost`, `capture_devices`, `apps`, `output_devices` and `Watcher`. Common code (`host.rs` `StreamHost`/`Chores`, `output.rs` `OutputPlan`, `suspend.rs`, `capture/intake.rs` `Intake`) never names a backend type directly.
- Linux output is a direct PipeWire F32 stream (`pipewire/output.rs`, `RT_PROCESS`, `node.latency` from `EngineConfig::buffer_size`, 48 kHz stereo unless the config or the graph's `default.clock.rate` says otherwise), planned on the `rikka-audio` loop thread from one `Graph::read`. `AudioEngine::output_latency()` is the stream's measured delay.
- Windows output (`wasapi/`): the `rikka-audio` host thread (MTA, `IMMNotificationClient`) owns an `Output` whose `rikka-audio-render` thread (MMCSS "Pro Audio") renders event-driven shared-mode float32 at the endpoint's mix format; `IAudioClient3` low-latency periods when the buffer size is below the engine default. `convert::ToDevice` resamples and folds (`Pan`) the mixer's plan layout to the device. The default endpoint is followed (the mixer moves to a reopened `Output`); a named endpoint's loss or no device left marks `DeviceLost`. Suspend is `IAudioClient::Stop`.
- Windows capture: microphone = capture client; `SystemAudio`/render endpoints = `AUDCLNT_STREAMFLAGS_LOOPBACK` plus a silent keep-alive render stream unless `passive()`; `OtherApps`/`Apps` = process loopback (`ActivateAudioInterfaceAsync`, Windows 10 2004+), `Apps` mixing one tap per matching session process (`wasapi/sessions.rs`, key = exe stem). `node_name` has no Windows meaning.
- The callback never allocates, locks or blocks; `tests/machine.rs` (`playback`) checks it on a real device with an allocation-counting allocator on PipeWire's `data-loop` threads.
- On Linux the engine and capture threads are `rikka_pipewire::LoopWorker`s. A stream's producer (the `rikka-audio-stream` decoder `Worker` owned by its `StreamSource`, or an `AudioFeed` writer) sleeps on a `rikka_worker` eventfd in `StreamShared` until half a ring is free, a flush completes, or it is resumed; handle commands and the source's drop call `notify_producer`. `AudioFeed` and `AudioCapture` are `AsFd` on unix and `AsHandle` on Windows.
- Finished voices leave the audio thread as `mixer::Retired` and drop on the host thread. Every sample and command queue is a `rikka_ring::channel`; wake-ups are eventfds.
- Dropping a `PlaybackHandle` does not stop the sound. `PlaybackHandle::watch(|PlaybackEvent|) -> PlaybackWatch` calls on the host thread: `Progressed` at most every 100 ms while the position moves and `Finished` exactly once when the retired voice drops; the mixer thread never calls listeners. `flush` drops what is queued.
- `Track::stream|load(path, PlayParams)` owns its own engine and one playback: `play`/`play_from` restart a finished handle with the carried volume, `set_volume` clamps to 0..1, `audible_position()` subtracts output latency, `on_change` follows it across restarts, dropping it stops the sound. Viewer, Animate and Discord use it.
- `AudioEngine::feed(rate, channels)` returns a handle plus an `AudioFeed`: blocking `write` pushes PCM from another decoder (resampled on the writer's thread, about 200 ms queued). `wait_until_queued_below(threshold, timeout)` returns early when the playback stops; `AudioFeed` is `AsFd` and `watch_queued_below(threshold)` arms it for poll loops (readable once room frees, on seek/flush/stop and when the engine loses its device).
- `Pan::new(pan, source, output).mix(src, gain_range, dest)` adds offline sound with the engine's pan law and fold.
- `AudioEngine::devices()` lists outputs (`OutputDevice { name, is_default }`), `AudioCapture::devices()` inputs (sources as `Microphone`, sinks and duplex nodes as `SystemAudio`); names are `node.description`s, accepted back by `EngineConfig::device_name` and `CaptureSource::Named`.
- Capture is the one desktop-sound stack: Replay, Remote, Discord Go Live, the recorder, Settings, the desk widgets and rikka-sound's spectrum capture through it. `CaptureSource::SystemAudio` captures the default sink's monitor (everything the speakers play, the caller included; the sink keeps running, so quiet arrives as zero samples, unless `CaptureConfig::passive()` lets it suspend). `CaptureConfig::node_name` replaces the default `rikka-audio-capture`.
- `OtherApps` and `Apps(keys)` make an unconnected stream and link the `Stream/Output/Audio` ports of every other process's apps, or of the chosen app keys (binary, else app name, lowercased), through `link-factory`, relinking as nodes come and go (`capture/apps.rs`; `AudioCapture::apps()` never lists the caller).
- One read contract for all sources: `fill(block, wait)` answers `Fill::Filled`, `Silent` (less than a block within `wait`) or `Ended` (stream lost); `read`/`wait_readable` serve the microphone path with whole frames. `AudioCapture` is `AsFd` (rung on data, stream or server loss), so one thread can poll several captures and its stop fd.
- `SoundSender::start(capture, SoundEncoding::new(thread, OpusApplication, frame).bitrate(b), sink)` is the one capture→Opus worker (48 kHz captures, default 128 kbit/s): it hands `Sent::Packet { data, at }` (`at` in samples, jumping to the wall clock after `Silent`) and `Sent::Quiet` once 500 ms stay below −80 dBFS; the sink returns `ControlFlow`. It waits on its command eventfd and the capture's fd; only the 100 ms stall that declares silence is timed. rikka-remote and discord-voice's `Soundshare` keep only their sink.
- `DeviceWatch::start(callback)` runs a `rikka-audio-devices` registry thread reporting `DeviceEvent::Added { id, name, direction } | Removed { id }` for Audio/Source, Sink and Duplex nodes.
- Format errors are typed: `Error::NoChannels(Role)`, `TooManyChannels { role, channels, most }` with `Role::{Output, Input, Feed, Source}`; `Error::PipeWire` (unix) and `Error::Wasapi` (windows) carry the sound system's error.
