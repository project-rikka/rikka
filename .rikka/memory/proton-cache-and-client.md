- `rikka-proton-cache`: one `cache.sqlite` per account folder (0700 dir, 0600 file, WAL, `synchronous=FULL`, `secure_delete`), written by a `rikka-proton-cache` writer thread; `flush()` waits for disk. Two HMAC-derived keys from the caller's `SymmetricKey`: AES-256-GCM for values, keyed hashes for ids, so no plaintext ids or values reach disk.
- Records are `Table<T>` (`Table::new(name)`, or `Table::bounded(name, max_records)` which evicts least recently used rows on write, as mail messages, conversations, listing pages and contact verifiers do; a record that no longer opens or decodes reads as missing and is deleted by a conditional `Op::Discard`), `Batch` lands whole, `Slot<T>`/`Staged<T>` keep the newest staged write (per-slot generation counter), `BlobArea` is a size-bounded LRU, `Wired<T>` keeps raw wire JSON beside the value. The private `Overlay` (`overlay.rs`, 4096-record LRU keyed by `CacheKey { table, id }`) makes pending writes readable at once until the writer thread reports them `Committed`. `retire()` bumps the era and wipes; older handles' writes are dropped. The schema stays at `user_version` 1: a file whose tables lack the expected columns is dropped and rebuilt on open.
- Store wire (still end-to-end-encrypted) objects and locked keys, never decrypted secrets. Tables are `<product>.<thing>`; app tables use `app.`. Products get the cache through `Account::with_cache` and `for_account`.
- `rikka-proton-client` (public) holds only what every product shares and depends on no product: `Proton` (one `Account` plus the CT `LogLists`; `builder()…build()`, `account()`, `log_lists()`, `with_cache`, `sign_in`, `unlock`, `unlock_with_passphrase`, `resume`, `resume_cached`, `unlocked(keys)`, `sign_out`), `Session`, `Accounts`, `EventLoop`, `Watch`, `Renewal`, sealed files. Reach the transport as `proton.account().api()`. Error variants are boxed; `Error::api()` reaches the API error.
- `Session` = `Proton` + `Arc<AccountKeys>`: `proton`, `keys`, `event_loop`, `renew`, `sign_out` (sign-out also retires the cache). Callers build product clients themselves with `for_account(session.proton().account(), session.keys())`. `renew()` answers `Renewal::{Unchanged, Updated, Rekeyed}`; on `Updated` (same keys, changed profile) the caller re-keys its clients with `with_keys` so their caches survive, on `Rekeyed` it builds new ones.
- `Accounts` (`ProtonBuilder::accounts(root, key)`): `list, primary, set_primary, state, signing_in, adopt, proton, resume, disable, remove`; states `Ready/Disabled/Removed`. Layout `<root>/accounts.sealed` + `<root>/<sha256(user)[..16] hex>/{session.sealed, cache/}`, each with its own derived key; sessions share one transport via `Api::with_session_store`.
- `session.event_loop::<C>().every(..).feed(feed, into).start()` → `Watch<C>` (`Stream` of `Change<C>`: `Product(C)`, `Refreshed(Refresh)`, `Renewed(Renewal)`, `SignedOut`). The caller registers any `rikka_proton_account::Feed` with a mapping into its own change type (`.feed(mail, Update::Mail)`). `start()` needs no Tokio runtime (UI threads call it); the loop task spawns on the `Watch`'s first poll and stops when it drops. Each tick walks the core cursor itself (every feed's `apply_core` in one blocking batch, then refreshes, and a key renewal when User/Addresses change or Refresh asks), then polls all feeds concurrently with the current keys; a feed's emitted changes are sent after its poll. Expiry gives `Change::SignedOut`. 30 s cadence, doubling backoff to 10 min with jitter.
- `SealedFile`/`SealedSessionStore` (public) are sealed JSON files and a sealed `SessionStore`; durable 0600 writes and 0700 folders live in `rikka_proton_api::private_file`. `SealedFile::read` reports a file sealed under another key or undecodable as `io::ErrorKind::InvalidData`; `SealedSessionStore::load` treats that as no session (signed out), while `Accounts` refuses an unreadable account list. `Proton::unlocked(keys)` caches the profile; `unlock`/`resume` paths cache it once in `Account::unlock_profile`.
- The cache writer keeps a batch whose transaction failed and retries it with the next one, so pending writes stay readable; past 8192 pending operations it drops them and reads fall back to disk.
