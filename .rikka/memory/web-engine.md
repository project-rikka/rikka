---
title: Web engine (rikka-web over official Google Chrome)
description: rikka-web runs official Chrome in kiosk mode on a nested display and drives it through its own MV3 extension.
about: crates/web/rikka-web
tags: [web, architecture]
---

- `crates/web/rikka-web` is the only crate that talks to Chrome; Music and Discord use its `SignInPortal`, the browser everything. No CDP: control is an MV3 extension plus Native Messaging, so pages never see automation (`navigator.webdriver`).
- `Runtime` = one Chrome (`RIKKA_CHROME_PATH`, else `/etc/rikka/web/chrome`; never `PATH`) per user-data-dir (`Profile::Persistent(dir)` keeps profile data, `Ephemeral` is a temp dir; Chrome never restores its last session, and windows it opens on its own before the first hello, such as the New Tab window, are closed by the first survey). Flags: `--kiosk --ozone-platform=wayland --password-store=gnome-libsecret …`, `WAYLAND_DISPLAY` = its `rikka-nested` socket, `RIKKA_WEB_CHANNEL` = a 0700 socket under `$XDG_RUNTIME_DIR/rikka-web-*`, plus `rikka_gpu_drivers::Drivers::environment()` so Chrome (from Rikka's nixpkgs) uses the pinned Mesa.
- Each start writes `<profile>/NativeMessagingHosts/os.rikka.web.json` pointing at `rikka-web-host` (`system/rikka-web-host`, found via `RIKKA_WEB_HOST_PATH`, then beside the program/`bin` as in dev session trees, then `/etc/rikka/web/host`), a byte pump between Chrome's stdio and the channel. The listener checks SO_PEERCRED and accepts reconnects (service-worker restarts); no hello within `EXTENSION_PATIENCE` → `RuntimeEvent::Failed(ExtensionMissing)`.
- Wire (`channel/`): NM framing (u32 native length + JSON; outgoing frames are capped at 1 MiB by Chrome). Rust sends `{call, api, args}`; `extension/background.js` dispatches generically into an allow-listed set of `chrome.*` namespaces plus `rikka.*` specials (`run`, `register`, `control`, `travel`, `favicon`, `edit`, `selection`) and forwards allow-listed `chrome.*` events, `rikka.page`/`rikka.post` from content scripts and `ask`s that Rust `answer`s; it reconnects the native port with doubling backoff. `PROTOCOL` must match on both sides (`Failure::ExtensionOutdated`). `Link` queues calls until hello, fails them on disconnect and refuses them while the runtime has reported `Failed`; every `call_then` continuation runs exactly once (oversized calls settle with an error); `call` gives a future, `call_then` a continuation on the channel thread.
- Back/forward: `PageState.can_go_back/forward` come from `runtime/joint.rs` (`JointHistory` per session), fed by top-frame `webNavigation` commits and corrected by `page.js` reports (`history.length`, `navigation.activation`/`currententrychange` type, same-origin entries); adopted tabs are asked to report once. `Session::back/forward` use `tabs.goBack/goForward` and fall back to `history.go` because Chrome refuses to go back to entries that never had a user activation (also after `tabs.update` navigations).
- A `Session` is one Chrome tab alone in its own fullscreen window. Opening: a view claims `Claim::title("rikka-claim-<random>")`, `windows.create(claim.html#token)`; once nested attaches that toplevel the real tab is created (or an orphan tab moved in) and the claim tab removed and deleted from history. Chrome popup windows cannot take moved tabs, so adopted popups and DevTools windows pair with `Unclaimed` toplevels by title (`runtime/sessions.rs::pair`).
- Tabs Chrome opens itself (target=_blank, window.open) become orphans offered as `NewSessionRequest` (`Opening::{Foreground,Background}Tab, Popup, Window}`) on the opener's `Event::NewSession` or `RuntimeEvent::NewSession`; `open()` adopts, drop denies (closes the tab).
- Chrome's own UI stays Chrome's: autofill and password bubbles, permission prompts, `<select>`, dialogs, find bar and print preview appear as popups or dependent toplevels over the page.
- `--kiosk` disables Chrome's page context menu and hides its link status bubble, so apps draw both. `extension/context.js` (static content script, all frames, isolated world) reports a `contextmenu` the page did not `preventDefault()` as `Event::ContextMenu(ContextMenu)` (link, image, media, selection, editable, frame id/URL; `at` is the right press `web_view` saw, relative to the view, `None` from the keyboard) and the link under the pointer or keyboard focus as `PageState.hovered_link`. Menu actions: `Session::edit(frame, EditCommand)` (`execCommand`; `Paste(text)` inserts text), `selection(frame)`, `inspect()` (Ctrl+Shift+I delivered to the nested view; no extension API opens DevTools).
- Scripts: no eval; every script ships inside the extension under `scripts/<owner>/<file>.js` (`rikka_web_extension` in `extension/defs.bzl`, core files listed once in its `CORE`; the shipped zip is `//system/rikka-web-host:extension`, whose `scripts` dict lists app script files exported to it). `Run::load(Script::bundled(path)).call(name)` injects a file that registers `globalThis[Symbol.for("rikka")][name]` and calls it; `Runtime::register(UserScript)` registers content scripts for this browser session only (while any page-world one is registered, `relay.js` runs on all pages and frames and forwards `window.postMessage({"rikka-message": name, body})`). A content script can inject another bundled file into its own document with `await chrome.runtime.sendMessage({ rikka: "load", script: "<owner>/<file>.js" })` (resolves `true`/`false`). Apps can also ship extension pages there and open them with `Runtime::bundled_page(path)`; the browser's reader page (`browser-reader/reader.html`) asks for its document in 128 KiB parts (`browser_reader::serve`) and writes it in, so long articles stay under the frame limit.
- Typed APIs over the bridge: `history()`, `bookmarks()`, `downloads()` (+ `RuntimeEvent::Downloads` snapshots, refreshed every 500 ms while one runs), `storage()` (browsingData, cookies incl. HttpOnly), `extensions()` (management), `privacy()`, `devices()` (synced tabs), `account()`.
- Deployment: the extension id derives from a public seed (`rikka-web-crx::Identity::rikka()`). `xtask dist build` signs `//system/rikka-web-host:extension` (a `ChromeExtension` in `base`'s system contents) as `share/rikka/web/<id>.crx` stamped `<release version>.<commit count>`, so local rebuilds at later commits update it too, and records `{id, version, crx}` in the entry's `extensions`; the dist NixOS module writes the force-install policy to `/etc/rikka/web/policies/managed/rikka.json` with a `file://` update manifest under `/etc/rikka/web/updates/`. The Native Messaging manifest names the host by its unresolved path (`/etc/rikka/web/host`), so it survives system updates. Dev runs (`xtask app` sets `RIKKA_WEB_HOST_PATH`) talk to the installed extension, so a changed `PROTOCOL` shows `ExtensionOutdated` until it is installed.
- Chrome is private to Rikka (`process/isolation.rs`): it is spawned in its own user and mount namespace (`pre_exec`, allocation-free rustix calls) where `/etc/rikka/web/policies` is bound over `/etc/opt/chrome/policies` (an empty tmpfs when Rikka has no policy; `PolicyMountMissing` when the policy exists but the mount point, which the module creates with tmpfiles, does not) and the profile's `Rikka Applications` over `$XDG_DATA_HOME/applications`, so policies never reach a Google Chrome the person installs and web-app desktop entries never reach the launcher. `CHROME_DEVEL_SANDBOX` is withheld because setuid sandboxes do not work inside the namespace. The module keeps Chrome outside `systemPackages`, so no desktop entry, `PATH` command or MIME handler exposes it.
- Tests: `rikka_web_machine_test` (`extension/defs.bzl`) runs real Chrome (`NIX["chrome"]` from the dev shell's `local` paths) through `rikka-test-chrome`, which unpacks the test's `rikka_web_extension(testonly)` with the Rikka key and loads it over `--remote-debugging-pipe`. It enters a nested user and mount namespace with an empty tmpfs over `/etc/opt/chrome/policies`, so on a machine with Rikka installed the force-installed extension of the same id does not replace the test extension.
