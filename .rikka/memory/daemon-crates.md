---
title: Sound, network, Bluetooth, power and battery crates
description: What each read daemon crate publishes and the rules its operations follow; none owns UI.
about: crates/daemons
tags: [daemons, connectivity]
---

- `rikka_sound::Sound`: whole PipeWire graph snapshots plus volume, mute, defaults, route, profile, clock, latency, meters. `Sound::allow_rates(&[u32])` writes `clock.allowed-rates` into the live `settings` metadata (writes before the metadata binds are held in `Session::unsaid`); the persistent counterpart is `GraphTuning`'s drop-in.
- `rikka_sound::Spectrum::listen(bands)` opens a passive, mono `rikka_audio::AudioCapture` of `CaptureSource::SystemAudio` named `rikka-spectrum` (hidden from the graph, like meters) and does the FFT (`rikka_fft::RealFft`) lazily inside `read(&mut [f32])`: it drains what arrived, analyses at most once per hop and resamples to any bar count, reporting silence once nothing arrived for 250 ms. No thread of its own.
- Graph work stays on its worker. Faders are cubic while stored amplitude is linear. Rate, buffer and format overrides are owned PipeWire/WirePlumber drop-ins.
- ALSA sinks/sources carry `Node.hardware`: formats and rate span learnt from `EnumFormat` queries taken while the card is not pinned, widened only, kept in `$XDG_STATE_HOME/rikka/sound/hardware`. A pinned format with no PCM offer sets `refuses_pinned_format`.
- Format queries (`session/format_query.rs`, `FormatQuery`) run `enum_params` plus `core.sync`, one per node at a time, re-run when the node's EnumFormat serial flips; PipeWire's param `seq` is its own async message number, not the caller's. Pins come from the follower's Props `params` struct.
- `Command::Tune { node, tuning }` applies a `DeviceTuning` live through Props `params` (unset = SPA default) and suspends the node so it renegotiates; the drop-in alone only acts once WirePlumber recreates the node.
- Sound binds the `default` metadata (default devices, per-stream `target.object`) once and follows its property events, like `settings`. It needs PipeWire ≥ 1.6.9: older module-metadata stopped broadcasting to existing clients after any client unbound before its pong (upstream #5445). Own writes show at once (optimistic); the node's `target` prefers the metadata over its props.
- `rikka_network::Network`: devices, grouped APs (same name and security deduplicated; strongest, then active, then saved), profiles, scan, join, leave, radios.
- `rikka_network::Invitation` is the one owner of the `WIFI:` share format (`Display` writes, `FromStr` reads incl. quotes, escapes, `R:` WPA3-only, EAP types); it draws nothing: callers encode `to_string()` with `rikka_barcode::QrCode`. `Network::accept(&Invitation)` joins (saved → saves the code's passphrase then activates, visible → beacon security, hidden only if `H:true`) or returns `Unjoinable`; `Joining::follow(&State)` turns states into `Progress`, counting only join/activate/save refusals and disconnects that carry a failure.
- `State::error` is a `rikka_bus::Refused<Action>` (see the daemon-integration note), so followers can tell which request failed; `send` clears it. `Network` and `Bluez` keep a `ManagedObjects` cache followed by signals; requests do not reread, their effects arrive as signals.
- Beacons decide security, and callers give only missing secrets. Hidden networks need explicit security. New profiles are per-user; all-users may prompt polkit.
- Edits keep unmodelled fields, and all secrets are replaced only on an intentional change. Parsed saved connections are cached by object path; a connection's `Updated` signal drops its entry, removal drops it and a new path is read once.
- `rikka_network::Tunnels` adds in-memory VPN connections (`WireGuardTunnel`, NetworkManager-openvpn `OpenVpnTunnel` in `connection-type tls`, Proton's `ProtunTunnel` for WireGuard over TCP/TLS when its plugin is installed; `TunnelKind::is_installed()`), activates, deactivates, removes them and streams `TunnelState`. DNS goes through the tunnel; secrets are stored with flags 0 because there is no secret agent. WireGuard file import goes through `WireGuardTunnel::from_config`.
- `rikka_bluetooth::Bluetooth`: adapters, devices, radio, connect. The full service adds pair, trust, block, rename and prompts.
- BlueZ allows one agent, so `Bluetooth::start()` only watches and `Bluetooth::answering()` (Settings) registers the agent; the shell observes without stealing Settings' prompts. Pairing answers bypass the blocked thread. Known devices include paired or trusted ones that are absent.
- `rikka_power::Power`: logind actions (shown for `yes`/`challenge`, absent otherwise), backlight, `PowerCapabilities` (`allows(Action)`, `hibernates()` outside `Action::ALL`), last error.
- Backlight reads sysfs and writes through logind (firmware > platform > raw), never reaching zero. `supersedes` collapses drag bursts. Logind is not watched.
- `rikka_battery::Battery`: `State { main: Option<Reading>, on_battery, devices, packs, history, error }`; `main()` is the UPower display device (level, direction, time, `Warning`, energy rate), `devices` are peripheral batteries (exact `charge` or coarse `Level`), `packs` the system's own batteries (health from `Capacity`, energies, cycles, `Threshold` when `ChargeThresholdSupported`). `preserve(pack, on)` calls `EnableChargeThreshold`; `read_history(span, points)` fills `history` from `GetHistory("charge")` of the first pack (bursts collapse). Pending states show their eventual direction. Only signalled paths are reread (relisting on DeviceAdded/Removed); bars follow `main_changes()`. Read failures are empty state; `error` is the last refused request.
- `rikka_timedate::TimeDate` follows timedated (zone, local RTC, `CanNTP`/`NTP`/`NTPSynchronized`) plus timesyncd's server name; timesyncd's property signals stand in for `NTPSynchronized`, which timedated never signals. `set_time(SystemTime)` is an interactive (polkit) `SetTime`.
- `rikka-net` is app HTTP. `rikka-network` is host connectivity.
