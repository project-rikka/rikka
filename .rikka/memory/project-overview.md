---
title: Rikka project map and layering
description: Top-level directories, the apps/system → public crates rule, layer conventions, and project-wide gaps.
tags: [overview, architecture]
---

- Linux-only NixOS desktop: own Wayland compositor plus a Vulkan UI stack. Rust 2024, every crate `0.1.0`, no crate published to a registry. Licensed GPL-3.0-or-later (`LICENSE`); ported third-party code is credited in `THIRD_PARTY.md` beside its layer (Blender for `crates/model`), and third-party test assets carry their own `LICENSE.md` or the author's readme.
- Top level: libraries live only in `crates/<layer>/rikka-<name>` (app-private ones in `apps/<group>/<app>/crates/`); executables only in `apps/` (user apps) and `system/`. There is no `libs/`.
- `system/`: `rikka-compositor`, `rikka-shell`, `rikka-cli` (the `rikka` command), `rikka-nixctl` (privileged NixOS service), `rikka-cast` (ScreenCast portal), `rikka-keyring` (Secret Service daemon), `rikka-pam-helper` (one PAM conversation for `rikka-pam`), `rikka-boost` (GPU clock boost), `rikka-replay` (instant replay), `rikka-remote` (QUIC remote desktop server).
- `apps/system/` (Linux only, bound to the Rikka session): ade, browser, calculator, discord, files, music, packages, settings, task-manager, terminal, updates (system update logs), viewer. `apps/general/` (Linux and Windows): animate, cut, launcher (rikka-launcher, Minecraft), paint, remote (rikka-remote-viewer).
- `sdk/` is the application SDK (`librikka.so.0`, IDL `sdk/rikka.ridl`, committed bindings in `sdk/bindings/<language>/` for C, C++, Go, C#, Java and Python); see the SDK note.
- `minecraft/` is the Rikka Client Fabric mod, which draws rikka-ui over Minecraft's own Vulkan frames through the SDK's embedding API; see the Minecraft notes.
- `website/` is the public Astro site for Cloudflare Pages; see the website note.
- `docs/<language>/` holds user documentation, one file per topic with the same name in every language (`docs/en/installation.md`, `docs/ja/installation.md`); English is the source, other languages are twins kept in sync.
- `crates/` layer folders: `foundation`, `desktop`, `session`, `daemons`, `status`, `text`, `graphics`, `media`, `model`, `physics`, `ui`, `ai`, `compositor`, `nix`, `remote`, `web`; the internal-crates-map note gives each crate's role. Every crate there is named `rikka-*`, also implementations of foreign formats and services (`rikka-psd`, `rikka-oauth`, the Google Chrome driver `rikka-web`).
- `crates/compositor` holds `rikka-compositor-*` and the test harness `rikka-test-display`; no compositor library depends on the UI or the renderer. Outside the folder only `system/rikka-compositor` and `crates/ui/rikka-nested` (the in-process display `rikka-web` embeds Google Chrome with) use them. The Wayland codec both sides share lives in `crates/foundation`: `rikka-wayland-wire`, `rikka-wayland-scanner`, `rikka-wayland-protocols` (XML + shared enums) and `rikka-wayland-client`, the one client every Wayland client uses.
- `crates/text` is the hand-written text engine and layers one way: `rikka-text-unicode` → `rikka-text-font` → `rikka-text-shape` / `rikka-text-raster` / `rikka-text-catalog` → `rikka-text-layout` → `rikka-text-document`. `crates/graphics/rikka-text` is the Rikka layer on top and stays in graphics because it uses `rikka-svg`. Comparative benchmarks live in `benchmarks/` (see the benchmarks note); their comparator crates may not be used elsewhere.
- All physics lives in the `crates/physics` layer, every crate named `rikka-physics-*`; see the physics-layer note. The CPU engine layers one way: math → core → geometry → collision → rigid → `rikka-physics-world` (rigid-only facade).
- Apps and system binaries depend directly on the public crates (`//visibility:public` on their `rikka_library`, see the public-crates note); there is no facade crate. The only runnable usage examples are the SDK's, in `sdk/examples/<language>/` (see the SDK examples note); the Rust crates have none.
- `installer/` reaches only `crates/nix` (`rikka-nix-edit`, `rikka-nixos-layout`, and `rikka-test-nixfmt` in tests). `reference/` holds git-ignored clones of upstream clients, read for protocol facts only, never copied.
- Rule: `apps|system → public crates`. A missing capability goes into its owning crate; a crate apps need is marked public, never wrapped.
- Third-party crates are declared once in `third_party/rust/crates.MODULE.bazel`; a crate lists only the ones it uses itself (x11rb, xkbcommon), never through a wrapper.
- App-private logic lives in `apps/<name>/crates/*`. Those crates use only public crates and external crates, and only their own app depends on them.
- Layers are Bazel visibility: internal crates are used only inside `crates/`, `benchmarks/` and `xtask`; public crates also by apps and system binaries; app-private crates only by their app.
- Runtime: the compositor starts first, hosts settings and seam IPC, starts the shell and outlives it. The shell is one process holding every desktop surface.
- Persistent data lives under XDG base dirs in `rikka/` (exceptions kept where they are: `rikka-ade/`, `rikka-shell/assistant`). There is no `RIKKA_HOME`.
- Gaps: CI is only the RBE image and website workflows; releases are made locally with `xtask release` (see the distribution note). No feature matrix: features are unified across the workspace, so each crate builds once with one feature set. The distribution's NixOS module is built and evaluated but never boot-tested.
- x86_64 is the only CPU: `flake.nix` exports one system (x86_64-linux), `install.sh` refuses other CPUs, the installer hard-codes x86_64 GPT types and 32-bit graphics, and `rikka-simd` fails to compile elsewhere. Windows x86_64 is a second OS only for `apps/general/` and the crates they reach (bazel-build note).
- Desktop-wide absences: no accessibility (AT-SPI), no printing, no media/volume/brightness keys or OSD. Secrets live only in the keyring (see the keyring note).
