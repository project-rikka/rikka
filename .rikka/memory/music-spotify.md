- Four app-private crates sit under the `music-spotify` adapter; no librespot, rust-protobuf or Shannon crate is used. Messages are hand-written `prost::Message` structs; proto2 fields whose presence matters are `Option`.
- `music-spotify-wire` is sans-IO: `Shannon`, `Handshake::new(rng)` → `hello()`, `response_len`, `finish(response)` → `Established { reply, keys }` (768-bit DH, RSA/SHA-1 check of the server key, HMAC-SHA1 key derivation), `Encoder`/`Decoder` frames, `Packet` constructors (login, pong, audio key request), `Incoming::read`, `Product::parse` (lenient XML), `SpotifyId`, `FileId`, `DeviceId` and hashcash `solve`.
- Its tests check Shannon against Qualcomm's reference vectors and replay an exchange recorded from a live access point (fixed randomness, bogus stored credentials answered with `BadCredentials`, files `tests/fixtures/ap-*.bin`); any change to the hello, reply, login frame or key derivation fails them, and re-recording takes a scratch binary.
- `music-spotify-session`: `Session::sign_in(token, device)` logs in with the OAuth token only to get reusable credentials, then connects with them exactly like `Session::connect(stored, device)` on resume. It resolves access points (apresolve, fallback `ap.spotify.com:443`), runs one link task (Ping/Pong keepalive, audio keys by sequence), publishes country and `Product` through a watch, and `connect` returns once product info arrived. `audio_key` reconnects once when the link closed or the answer took over 1.5 s.
- `music-spotify-api`: `SpClient::new(device, stored)` resolves an spclient host and keeps a client token (`ClientTokenExchange`) and a login5 access token (`Login5Exchange`, stored credential with the keymaster `CLIENT_ID`); both exchanges are sans-IO and answer hashcash challenges. Endpoints: `entities::<Track|Album|Artist>`, `rootlist`, `playlist`, playlist edits, `saved`/`set_saved`, `search`, `radio`, `audio_urls` (`CdnUrl` expiry read from the CDN signature, 5 min margin). Nothing retries.
- The adapter signs in with PKCE on 127.0.0.1:8898, keeps `{username, auth_data}` (base64) as the keyring `credentials`, and refuses non-premium products (`NotEntitled`, also for the AP's `PremiumAccountRequired`) before keeping anything. All network work runs on the `rikka-spotify` tokio runtime (`worker::run`; `worker::wait` blocks `Origin::open`).
- Playback is a `SpotifyOrigin` on the shared `Streamer`: extended metadata → `Listener::file` (explicit filter, release dates, catalogue/country restrictions, then the track's or an alternative's Ogg Vorbis file by quality 320/160/96) → audio key (`AudioKeys`, remembered per file id; a denied key is `Error::Refused`) joined with `audio_urls` → the length from a `bytes=0-0` Content-Range → 1 MiB ranges. No volume normalisation is applied.
- The kept file is a `music_spotify_audio::Label` (`RKSPOTFY` header, track gid, file id) followed by the CDN's encrypted bytes; no key is stored. `Origin::open` reads the label, asks `AudioKeys` (a session round trip for files kept by an earlier run) and serves `Decrypted`: AES-128-CTR with Spotify's fixed IV, audio from 0xA7 bytes in, which leaves plain Ogg Vorbis.
- Only `music-spotify-audio` compiles AES (`cranelift = False`); `Decrypted::new` takes a `Box<dyn StreamReader>` so the cipher is never monomorphized into a Cranelift-built crate.
