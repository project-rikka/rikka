- Events go deepest-first with bubbling; anchored elements are hit first, latest first. `grabs_keys` (only `shortcut_field`) takes compositor chords.
- Focus follows presses: only a non-side-button press moves it, to the nearest focusable ancestor-or-self of the deepest hit node (within the top modal); a press inside the top modal with no focusable node on its path clears focus (web-style blur), unless a handler calls `keep_focus` (window chrome, focusless controls), and a release never changes focus. `autofocus` and `claims_focus` also give focus; an `AUTOFOCUS` widget takes it back whenever focus clears.
- `Event::Pad(PadInput)` (tablet pad buttons, rings, strips, dials) is delivered to the focus chain like `KeyReleased`/`Commit`.
- Handlers override focus: `request_focus` focuses its own node (or its nearest focusable ancestor), `EventCtx::keep_focus` leaves focus untouched for this press (focusless controls, Cut's timeline), `EventCtx::return_focus` hands it back to whatever held it before (transient popups such as `menu_bar`). With nothing focused, keys go along the path of the last non-side-button press, else the root. `focusless()` `container`, `button` and `combo` are not tab stops and keep focus where it was.
- While a widget holds the pointer capture its release reaches only that widget. Focus and capture requests (`request_focus`, `return_focus`, `capture_pointer`, `release_pointer`) take effect from every delivery, including synthesized `FocusLost`/`FocusGained` and hover refreshes (`settle_requests`).
- Click counts (`EventCtx::presses`, `runtime/presses.rs`) are per node: a press within 500 ms and 5 px of the last continues the series only for nodes that received the previous press (the caption toggles maximize on its own empty area on every even count).
- Pointer interception (`runtime/dispatch.rs`): every `Behavior::INTERCEPTS` ancestor on a press/move/release path, outermost first, sees the event before the target; calling `capture_pointer()` there claims the stream, every node beneath gets `Event::PointerCancelled` and the claimer becomes the captor. Scroll events are not intercepted. Interceptors above the deepest `MODAL` on the path never see the stream, and `capture_pointer_exclusively()` (open menus, menu bars, combo lists) keeps every interceptor out of the captor's stream.
- Modals (`Behavior::MODAL`: `popover`, dismissable menus, `sheet`) own the keyboard: focus, autofocus and Tab order stay inside the top modal, keys go to it and bubble no further (window `on_chord`/`on_command` bindings stay silent; unclaimed commands still reach rikka-app), and presses outside reach the modals first. A press outside every modal goes to a captor inside a modal (a menu with an open submenu) first, then the other modals, then, if still unhandled, whatever lies beneath (a right click elsewhere reopens a context menu there). Popovers consume presses, releases, scrolls and gestures inside them. Focus held before it opened is parked and handed back when it closes.
- Standard commands (`rikka_ui::Command`, from rikka-input): a key press or Back/Forward side-button press is delivered per node as the raw event, then, if unhandled, as `Event::Command` before bubbling on, so a deeper widget's meaning beats an ancestor's raw chord. Side buttons follow the pointer path, fire on press only and never move focus. The unclaimed command is left in `Ui::take_unclaimed_command()`.
- Text editing, selectable rich text, find bars and the terminal grid act on commands (clipboard, undo, select all, find next), not letter chords; `container(..).on_command(command, handler)` binds one. `Command::ContextMenu` comes from the Menu key and Shift+F10. `send_command(command)` queues a command that `Ui::render` delivers to the keyboard target once the tree has settled.
- `PaintCtx::topmost(draw)` paints above everything (z 2), ignoring every clip; context menus use it to escape a `CLIPS` host. `point_panel(at, size, viewport)` places a panel at a pointer, flipping at the window edges.
- Under `PaintCtx::set_subtree_scale` hit routes (anchored ones included) and delivered pointer positions are unzoomed through `runtime/zoom.rs`, so zoomed controls are hit where drawn; the paint walk raises the `ZOOMED` table flag so unzoomed trees skip the lookups.
- `EventCtx::lock_pointer()` captures, hides the cursor and has rikka-app lock the pointer (zwp_pointer_constraints); the holder receives `Event::PointerTravelled(delta)` (unaccelerated) until `release_pointer()`. `Ui::pointer_locked` reports it.
- Pen input: `Ui::handle_input(event, Option<Stylus>)` (`handle_event` passes `None`) dispatches the normal pointer event (hover, capture, click counts, interception unchanged) and `EventCtx::stylus()` returns the `rikka_types::Stylus` only for `PointerMoved`/`Pressed`/`Released`/`Scroll` deliveries of that dispatch (synthesized enter/exit/cancel/command see `None`); `None` always means mouse or touch. Sample positions are in the event's coordinates and are unzoomed with it under `set_subtree_scale`. `Stylus::samples()` lists every coalesced sample oldest first, ending with `sample()`.
- `PaintCtx::fling(key, value, velocity)` restarts a motion with a velocity so a released gesture springs on.
- Drag and drop: `DragStart::new(Offer, DragIcon).actions(..)` (`rikka-app` builds the ghost `Ui`), targets answer `DragMoved` with `accept_drag(Accept)` and read `DragOffer` on `DragDropped { action }`. `Behavior::CATCHES_DROPS` gets a drag's motion before descendants; `drop_zone` uses it unless `content_first(true)`. `DragAction`/`DragActions` live in `rikka-types`; `DRAG_SLOP` is the one press-to-drag threshold; `Accept::copy_or_move` prefers a move only for this process's own drags.
- Editors drag their selection (copy/move, moves within one document in one undo step) and take text drops at a drop caret; selectable rich text drags as copy. `drag_chip` draws the shared drag icon.
- `Widget::window_part(bounds, point)` names a window control (`WindowPart::{Caption, Minimize, Maximize, Close, Resize(edge)}`); `Ui::window_part_at(point)` asks only the deepest hit node, so interactive children inside the caption stay client area. The title bar, its caption cells, caption buttons and resize edges answer it; Win32 hosts map it to `WM_NCHITTEST` codes.
