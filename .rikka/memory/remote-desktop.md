title: Remote desktop service (rikka-remote)
description: rikka-remote serves the live session over QUIC to rikka-remote-viewer: threads, encoding, recovery, pacing, auth.
about: system/rikka-remote
tags: [remote, streaming]
---

- `system/rikka-remote` is a session service (`rikka-remote.service`). It owns the `rikka.remote` settings domain and serves `rikka.remote` (`rikka_session::remote`: `status`, `disconnect`, event `changed`) on `remote.sock`. It idles while `enabled` is false. There is no web client; viewers speak `rikka-remote-wire` (spec in `crates/remote/rikka-remote-wire/PROTOCOL.md`).
- `server.rs`: one quinn endpoint on UDP `port` (default `rikka_remote_wire::DEFAULT_PORT`); `Hub` holds identity, access, notices, status and the single live viewer (a new viewer ends the old one with `Ended(Replaced)`; stopping waits up to 3 s for `Ended(Stopped)` to leave). Without `network`, only loopback and tailnet peers are admitted when `tailscale` is on: both the peer and the local address must be tailnet addresses (100.64/10, fd7a:115c:a1e0::/48). Encodable codecs are probed once on a blocking thread and cached only on success.
- `identity.rs`: self-signed certificate and key at `$XDG_STATE_HOME/rikka/remote/certificate.pem` (0600); its SHA-256 `Pin` is shown in Settings and pinned by viewers on first use. `access.rs` + app-private `remote-access`: PAM password (service `rikka-remote`, else `login`), `Throttle`, remembered device tokens (`devices`, hashed, 90-day expiry, 32 max).
- `viewer/`: `mod.rs` session handshake and live loop, `control.rs` control stream writer, `datagrams.rs` client datagrams (motion, feedback), `streams.rs` input and file streams, `sender.rs` (congestion → encoder bitrate, FEC protection from loss, `rikka_rate_control` pacer and congestion control, stats; a datagram quinn refuses is neither booked as sent nor given a sequence number), `recovery.rs` (lost frame or stall of max(300 ms, 4×RTT) → recovery frame from the client's newest good frame; `handled_through` dedupes).
- `media/`: `rikka-remote-video` `rikka_worker::Worker` (a `rikka_capture::BufferPool` of dmabufs + `rikka_vulkan_video::Encoder`, waiting on the compositor fd and its command eventfd), `rikka-remote-sound` (a `rikka_audio::SoundSender` over `CaptureSource::SystemAudio`: 10 ms LowDelay Opus stamped on the capture timeline, nothing sent while quiet; the redundant previous packet under loss is added by the viewer link), `rikka-remote-input` and `rikka-remote-clipboard` (`rikka_worker::Worker`s blocking on a command channel; input drives rikka-virtual-input with evdev keys). `Backlog` tells the video thread to skip capture while the pacer holds more than max(1.5 frames, 8 ms) and to abandon a still-picture refinement when a new frame arrives.
- Video: ext-image-copy capture into dmabufs imported zero-copy, H.265 preferred then H.264, size fitted to the viewer's viewport. Rate control changes in place (no IDR); intra only at stream start; loss is repaired by reference-frame invalidation. Still pictures get constant-QP refinements.
- Cursor shapes travel as straight RGBA `CursorShape` messages with serials in an LRU of `CURSOR_SHAPES` (wire constant); `Cursor(0)` while the compositor's cursor capture session reports the cursor left (also while an app hides it). Position datagrams only while the viewer holds a pointer lock; then buttons press where the host pointer is.
- Each viewer session follows the compositor's `rikka.pointer` seam (`rikka_session::pointer::modes` on `Hub::compositor`) and forwards it as `ServerMessage::PointerMode`; the compositor publishes `Relative` while the person's seat has an active pointer lock, or a confinement with a hidden cursor.
- The NixOS side (Settings app) opens UDP <port> on `tailscale0` (and globally with LAN access) and adds `security.pam.services.rikka-remote`.
