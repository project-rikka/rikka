about: crates/graphics/rikka-image

- `rikka_image::read(src)` (`ReadRequest`) offers `.decode() .animation() .probe()` and, for SVG, `.rasterize_svg() .rasterize_svg_to_fit(w, h)`, with options `.format .max_alloc .no_alloc_limit .max_dimensions .color_scheme(ColorScheme)` (re-exported from rikka-svg; light by default, it only answers SVG `prefers-color-scheme`). Exif orientation is always applied.
- Writing is `image.write(encoding)` (`WriteRequest`) `.quality()….to(path)|to_bytes()`, `encode(encoding)` or `save(path)`. A marker encoding (`Png`, `Jpeg`, `WebP`, `Avif`) links only its encoder; a runtime `Format` links every encoder. Options exist only where they act: `quality` on lossy encodings, `speed` on `Avif`, `compression` on `Png`/`WebP`, `lossless` on `WebP`.
- `Image { width, height, color, Pixels::{U8, U16, F32} }` is the crate's own; `ColorType` and `Orientation` are its own enums. Pixels leave as `rgba8() -> Cow<[u8]>`/`into_rgba8()` or, unquantized (HDR, EXR, deep pictures), `rgba32f() -> Cow<[f32]>`/`into_rgba32f()` and come back through `Image::from_rgba8/from_rgba16/from_rgba32f`. It knows nothing of the renderer.
- Own codecs: PNG and APNG through `rikka-png`; GIF, BMP, ICO, TGA, QOI, PNM/PAM, farbfeld, Radiance HDR and DDS (BC1–3, decode only) in `src/codecs/`, each `probe`/`decode`/`encode` over a byte slice. The `image` crate is only the backend in `codecs/foreign.rs` for JPEG and WebP decoding and JPEG encoding; none of its types leave that file.
- WebP is written by libwebp (lossy at `quality` unless `.lossless()`); `codecs/webp.rs` adds the ICC profile as a VP8X/ICCP chunk. `GifWriter::create(path, w, h, Loops)` + `push(Frame)` + `finish()` writes animated GIF (own LZW, exact palette up to 256 colours else median cut, alpha below 128 transparent, delays at least 20 ms).
- AVIF and HEIF (read; AVIF also written), JPEG XL, TIFF and OpenEXR (read and write) and JPEG 2000 (read) go through the internal `rikka-image-ffmpeg` behind the same doors (`Format::needs_ffmpeg`, adapter `codecs/ffmpeg.rs`). Its deps are rikka-ffmpeg, bytemuck, moxcms (JPEG XL colour profiles) and thiserror; `Animation` dispatches to `heif::Playback` or `jxl::Playback`.
- rikka-image-ffmpeg parses every container in Rust (ISOBMFF items, grids, `auxl` alpha, `irot`/`imir`, `clap`, `colr`, `avis`; TIFF IFD0; EXR header and chunk table; J2K `SIZ`, JP2 `colr`; JPEG XL boxes with `jxlc`/`jxlp` gathered and `brob` checked, then the codestream's SizeHeader and ImageMetadata through `jxl/bits.rs`) and admits the size before libavcodec decodes a codestream, so probing never loads FFmpeg and the in-house, JPEG and WebP paths never do.
- Deep AV1/HEVC become 16-bit, EXR stays float, premultiplied EXR/TIFF/HEIF/JPEG XL alpha is straightened. AV1 decodes with libdav1d, else libaom. AVIF is written by libaom-av1 (allintra, 4:4:4, 10-bit for deep pictures, alpha as a second stream) into a still-AVIF container written in Rust (`avif.rs`; `av1.rs` builds `av1C` as FFmpeg's muxer does) with an nclx `colr` and the ICC profile; TIFF gets its ICC tag added in Rust.
- JPEG XL decodes with FFmpeg's `libjxl` (whole file as one packet, bare codestream or container). libjxl applies the orientation itself, so the picture comes back upright at the displayed size while `probe` reports stored size plus orientation. Integer depths up to 8/16 bits stay U8/U16, float or deeper samples become F32; CMYK (a Black channel) is refused. The ICC profile comes from frame side data; an enum colour space other than sRGB gets a profile built by moxcms from the frame's CICP tags (gray pictures and unknown tags get none). Animations play coalesced frames with durations from `pkt_timebase` set to the AnimationHeader's ticks and `num_loops` as plays. Writing uses the `libjxl` encoder: `quality` maps to Butteraugli distance as libjxl's `JxlEncoderDistanceFromQuality` (100 is lossless), `speed` to effort 9…1, every `ColorType` kept, ICC attached as side data.
- Without FFmpeg or a codec: `Error::NeedsFfmpeg(format)`, `NeedsDecoder`/`NeedsEncoder { format, codec }`.
- Decoders never panic on damaged input: every output allocation is admitted by the request's limits (`codecs::Limits::admit`), sizes above 64 MiB must be plausible for the bytes present (`codecs::plausible`), a file read whole must fit `max_alloc`, and animations composite through `animated::Compositor`, which counts every canvas. The default limit is 512 MiB per picture.
- Detection is content-first (ISOBMFF `ftyp` brands tell AVIF from HEIF; JPEG XL by `FF 0A` or its `JXL ` signature box; TGA needs its extension or `.format`). Orientation comes from Exif in JPEG, WebP, TIFF and PNG's eXIf, HEIF `irot`/`imir` and the JPEG XL codestream. `Format::mime_types()` lists every MIME type a format answers to.
- `probe()` reads only headers and returns `ImageInfo` with `text` (PNG tEXt/zTXt/iTXt); `write(Png).text(&entries)` writes them (Files' thumbnail keys). An `Image` carries its ICC profile (`icc_profile`, `with_icc_profile`), which PNG, JPEG, WebP, AVIF, JPEG XL and TIFF writes embed.
- CPU operations are only `convert`, `crop`, `overlay`, `paste_in_place`, `apply_orientation` and resizing (`resize_exact`, `resize_to_fit`, `thumbnail`; `Filter::{Bilinear, Lanczos3}`), which resamples premultiplied in stored values through `rikka-image-resample`, in up to 8 row bands on `rikka-image-resample-N` threads. Editing geometry belongs to rikka-image-edit.
- `ImageLoader::read(src).thumbnail(w,h)|vector(w,h).color_scheme(s).submit()` runs on a lazy pool of at most 8; unstarted dropped jobs are cancelled. Each decode holds its cost against the shared `Budget` until its `LoadHandle` drops; oversized pictures run alone, so the budget slows decoding but never blocks it. `LoadHandle::follows_color_scheme()` tells whether a vector result answers the scheme.
- SVG is rikka-svg (svg-renderer note): parsed once, rasterized at draw size with a 64 Mpx cap; rikka-image hands it its decoder for embedded raster `<image>`s.
