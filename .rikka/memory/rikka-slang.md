---
title: Runtime Slang compiler (rikka-slang)
description: rikka-slang dlopens libslang, compiles Slang to Vulkan SPIR-V with embedded modules, reflects layouts and attributes.
about: crates/graphics/rikka-slang
tags: [shaders, graphics]
---

- Public crate. `Compiler::builder().modules(shaders::SLANG_LIBRARY).build()?` makes one Slang session; `.module(name, source)` adds one embedded module (`a.b` is served as `a/b.slang`). `compiler.compile(&Source::new(name, text).entry("fs").layout_of("Material"))` returns a `Program`; without `.entry` every `[shader(..)]` function is compiled.
- libslang is opened by soname (`libslang-compiler.so`, then `libslang.so`) through libloading on first use; it reaches binaries through the shell's `dlopened` RUNPATH. A `Compiler` holds up to 8 `Worker` slots (`worker.rs`), each its own `IGlobalSession` + `ISession` behind a mutex (sessions of one global session crash when used from two threads at once), created lazily. Each `compile`/`reflect` takes a free primary worker (`try_lock` over the slots, an opened one first, else opening an empty slot; when all 8 are busy it waits on one in turn), so concurrent compiles on one `Compiler` run in parallel; the primary also reflects. Helpers (capped process-wide at cores − 1, `Helpers`) take the remaining free slots and an entry index from an atomic counter, so one program's entries generate in parallel. Entry code generation dominates (≈0.1–3 s per entry at -O2; a fresh session parses the library ≈0.7 s, a global session ≈0.13 s). `Compiler::reflect(&source)` links without code generation (parameters, types, conformances; no entry points). `Compiler` is `Send + Sync`; share one per optimisation level rather than building one per thread.
- Windows: `slang-compiler.dll`, then `slang.dll`, loaded with `LoadLibraryExW(LOAD_LIBRARY_SEARCH_APPLICATION_DIR | LOAD_LIBRARY_SEARCH_SYSTEM32)` (`ffi::load_beside`; never the current directory). The SPIRV-Tools optimizer C API (`ffi/spirv_tools/{unix,windows}.rs`) comes from `slang-glslang.dll` or a loaded Slang DLL when they export it, else from `SPIRV-Tools-shared.dll` beside the executable; official Slang DLLs do not export it, so a Windows install must ship `SPIRV-Tools-shared.dll` or every compile fails at the flattened warm-up.
- Settings match `rikka-shader-build`'s slangc flags; both read `rikka_spirv::{SLANG_PROFILE (`spirv_1_6`), SLANG_QUIET_WARNINGS (39001 bindless binding overlap, 41012 profile upgrade), SLANG_WARNINGS_AS_ERRORS}`: scalar buffer layout, column-major matrices, `-O2`, plus precise floating point (the renderer package's `-fp-mode precise`): every float operation carries `NoContraction`. SPIR-V entry points are named `main`. `crates/graphics/rikka-spirv` (dependency-free, internal) owns the SPIR-V plumbing every shader crate shares: `words`/`bytes`, the `instructions(words)` walker (`Instruction { opcode, operands, end }`, lazily checked framing), `literal_string` and `invariant_position`.
- Precise floating point keeps renders bit-reproducible: NVIDIA may run one pipeline with differently fused (FMA) machine code over time, so contractible SPIR-V gives inputs-identical results a few ulps apart. It costs about 4 % of a 1080p look frame.
- Embedded modules are served by a Rust `ISlangFileSystem` COM object (`file_system.rs`); `ffi/` holds hand-written vtables checked against slang.h 2026.16 (`ISession` up to `loadModuleFromSourceString`, `IComponentType`, `IModule`) and the `spReflection*` C functions. COM pointers are `com::Com<Vtable>` (release on drop); session-owned `IModule`s are never released.
- Each compile loads the user source as a new module `<name>-<n>`, so recompiling the same name (hot reload) never returns a stale module. Loaded modules stay in their session (~0.5 MB per reload), so a worker that has loaded `RENEW_AFTER` (8) modules is renewed after the compile on a `rikka-slang-renew` thread: a fresh session that preloads the source just compiled, so the library is parsed (~0.8 s) off the critical path; a worker that reaches twice that inside compiles is recycled inline.
- Exit safety (`exit.rs`): compiles run on detached threads (renewals, the renderer's optimizer, apps' own threads), and libslang running while `exit()` runs its handlers segfaults in IR lowering (seen in 3D GPU tests). Every libslang call (`Compiler::build`, compile, reflect, renew, drop) holds `exit::busy()`; an `atexit` drain refuses new work (`Unavailable`) and waits for running work. Handlers run in reverse registration order and libslang, libslang-glslang/libglslang and their function-local statics register destructors lazily, so the drain is registered twice: in `ffi::load` right after dlopen with libslang-glslang preloaded, and after a one-time warm-up compile (`-O2` + flatten of a tiny vertex/fragment program) in the first `Worker::open`. Never register it only after a user compile, and never let libslang code run outside `busy()`. A `Compiler` dropped while exiting leaks its sessions.
- `CompilerBuilder::optimization(Optimization::{High, None})` picks `-O2` or `-O0` for that compiler's sessions. `-O2` is Slang's `-O0` IR plus spirv-opt's performance passes, which dominate (4–15 s for a lit material variant, 20–30× the `-O0` time). `Source::flatten()` runs a short SPIRV-Tools pipeline (wrap-opkill, dead branches, merge-return, exhaustive inlining, dead functions, ADCE — the first passes of `-O2`) on each entry in its worker; the inlined code keeps `NoContraction` and roughly halves the driver's pipeline build against raw `-O0`. SPIRV-Tools is not linked: `ffi/spirv_tools.rs` takes the optimizer C API from the library loaded with libslang (nixpkgs' unvendored glslang, `libglslang.so.*`), loading libslang's `libslang-glslang` beside it when needed; failures are `Error::Flatten`. `Source::conformance(type, interface)` asks reflection (`spReflection_isSubType`) and `Program::conforms` answers. Reflection does not expose `[constref]` on methods.
- Vertex entries get their Position output decorated `Invariant` (`rikka_spirv::invariant_position`; rikka-shader-build applies it to slangc output too). The layout types (`TypeLayout`, `Type`, `Field`, `Attribute`, `Argument`, `Stage`, …) are serde, so build tools can ship reflected layouts.
- `ParameterSchema::from_struct(layout, offset)` (serde) turns a reflected struct into `ParameterSpec`s: dotted names for nested structs, `ParameterKind` from the type plus attributes `Default`, `Range`, `SoftRange`, `Group` (inherited by nested fields), `Order`, `Label`, `Color`, `Srgb`, `Options("a|b")` (enum over int/uint), `Texture("colour|data|normal|ramp")` on a `RikkaTexture`, `Hint("angle|logarithmic|hidden|advanced")`, `Role("albedo|albedo_texture|emission|emission_texture|displacement")` (`ParameterSpec::role`, checked against the kind; `ParameterSchema::with_role` finds one), repeatable `Preset("names", values..)`; `merge` joins schemas and refuses duplicate names. The Slang attribute structs live in rikka's `rikka.material.attributes`; numeric attribute fields have defaults so `[Default(0.5)]` and `[Default(1, 2, 3)]` both work.
- `Program`: `entry_points()` (`EntryPoint { name, stage, workgroup_size, spirv: Vec<u32> }`), `parameters()` (global `Parameter { name, binding: Descriptor{set,binding} | PushConstant | Uniform{offset} | Unbound, layout }`), `type_layout(name)` for types asked with `layout_of` (`None` when the source has no such type; asking is never an error).
- `TypeLayout { ty, size }` with `Type::{Scalar, Vector, Matrix, Array{element,count: None = unsized,stride}, Struct{name, fields}, Pointer{pointee name}, ConstantBuffer, Resource{shape,arrayed,access}, Sampler, Other}`; offsets and sizes are the scalar layout the SPIR-V uses. `Field { name, offset, layout, attributes }`; user attributes (declared in Slang as `[__AttributeUsage(_AttributeTargets.Var)] struct RangeAttribute {..}`, used as `[Range(0, 1)]`) come back as `Attribute { name: "Range", arguments: [Argument::Int|Float|String] }`.
- Errors: `Unavailable` (libslang missing), `Compile { diagnostics }` (`failed to compile shader: {diagnostics}`), `MissingEntryPoint`, `UnknownType`, `UnsupportedStage`, `Call`, `Nul`, `Flatten`; schema problems are `SchemaError`.
