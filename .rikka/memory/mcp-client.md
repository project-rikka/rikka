- An in-house client, depending outward on `rikka-agent` and `rikka-tools`; no third-party MCP crate. Three inner layers, one-way: `protocol/` (hand-written serde types of revision 2025-11-25: `Message`, `ErrorObject`, `Listable`/`Page`, tools, prompts, resources, completion, content), `client/` (JSON-RPC `Connection` over a `Link`), then `session.rs`/`listing.rs`/`watcher.rs`.
- `Connection::open(link, arrivals)` runs one dispatch task: answers settle waiting requests by id, server requests get `ping` → `{}` and anything else → -32601, notifications go to the session's `Watcher` through a channel. A request future that is dropped (timeout) sends `notifications/cancelled`; `initialize` never does. The client declares no capabilities.
- `Link::Stdio` spawns the child (`kill_on_drop`, newline-delimited JSON, writes finish even if the caller is dropped). `Link::Http` is streamable HTTP over `rikka_net::Client` (its TLS, proxy and retry policy): POST with `Accept: application/json, text/event-stream`, `Mcp-Session-Id` and `MCP-Protocol-Version` headers, JSON or SSE answers, resumption with `Last-Event-ID` (`client/event_stream.rs`), a standalone GET stream for server notifications, re-initialization when the server forgets the session (404), `DELETE` on drop. The legacy HTTP+SSE transport is not spoken (`"type": "sse"` maps to streamable HTTP).
- HTTP 401, or 403 `insufficient_scope`, makes the server `needs_sign_in` with its `WWW-Authenticate` challenge kept for sign-in. `sign_in.rs` + `authorization.rs` (`Authority::discover`) run the MCP authorization flow over `rikka-oauth`: protected-resource metadata (challenge pointer on the same origin, else well-known), issuer metadata (else the 2025-03-26 default `/authorize`, `/token`, `/register`), declared client id or dynamic registration, PKCE S256, `resource` parameter, challenge-or-resource scopes plus `offline_access`, `iss` check. `credentials.rs` stores `{client_id, client_secret?, client_secret_basic, token_endpoint, resource, token}` and renews through `rikka_oauth::RefreshingToken` under the vault's file lock.
- `Hub::builder().place(Place::new(name, path).with_description(..)).folder(..).vault(..).build()` is the one entry point. Places are `.mcp.json` files; later places override earlier ones by server name.
- `hub.start()` connects once, then watches the place files. Each server gets a `ServerStatus`: reached (live `tools()`, `prompts()`, `resources()`, `resource_templates()`), disabled, needing sign-in or failed (stderr tail). `changes()` beats on any change, including `tools/`, `prompts/` and `resources/list_changed`.
- A session lists tools, prompts, resources and templates by the server's capabilities (`listing.rs` `Lister`); only a failed tool listing fails the server.
- `hub.toolkit_set()` is a `rikka_agent::ToolKitSet` with one `ToolKit` per reached server (about = title, instructions = the server's). Tools are `mcp__<server>__<tool>`, bounded and unique, deferred until ToolSearch loads them (`select:<server>`).
- Prompts are person-run commands named `<label>:<prompt>` (`Prompt::command`), listed per server as shared `Arc<[Prompt]>` by `ServerStatus::prompts()`: `hub.prompt(command)`, `hub.get_prompt(command, &values)` (positional values, the last argument takes the rest, required ones checked) returning `Prompted` parts (`Part::Text/Picture/Contents`), and `hub.complete(command, &given, typed)` over `completion/complete`.
- Resources are mentioned as `<label>:<uri>` (`Resource::mention`, `ResourceTemplate::mention_prefix`), listed per server by `ServerStatus::resources()`/`resource_templates()` (at most 10 000 resources kept): `hub.is_resource_mention`, `read_mention`, `read(server, uri)` returning `Contents` (`Body::Text/Bytes`, `into_body`).
- `hub.instruction()` is a standing instruction naming connected servers (marked *resources* when they offer some) and those awaiting sign-in; callers refit when its text changes.
- `hub.tool()` is the deferred `McpServers` tool (list/add/remove/enable/disable/sign_in/sign_out/reconnect). Changes are kept at once, without asking the person.
- `hub.resources_tool()` is the deferred `McpResources` tool (`list`, `read` with text cut at the prompt's `read_chars`), wired with `ToolboxBuilder::deferred`. `ToolCall::parse` names calls of both tools and of server tools.
- `Catalog` reads, merges (`Catalog::merge`) and writes `.mcp.json` (`Catalog::path_in(project)`), keeping unknown keys; `get`/`insert`/`remove` edit servers by name. `Http::new(url).with_header(..).with_oauth(..)` and `Server::with_disabled(..)` build entries. `Stdio::parse`/`line` convert shell-quoted command lines. `${VAR}` and `${VAR:-fallback}` are expanded in command, cwd, env, url, headers and oauth when a server starts.
- Remote OAuth credentials live in the keyring (schema `os.rikka.Mcp`, attribute `server`) through `Vault::from_runtime_dir()`, whose folder holds only the cross-process refresh locks; `sign_in` opens the browser and waits.
- `Hub::equip(ToolboxBuilder) -> ToolboxBuilder` adds the hub's shelf (`toolkit_set`) and the deferred `McpResources` and `McpServers` tools; hosts add `hub.instruction()` themselves where their standing blocks want it.
- Users: ADE (`apps/system/ade/src/project/hub.rs`: places `personal` and `project`'s `.mcp.json`) and the shell assistant (place `assistant`). The composer side is `rikka_chat`'s MCP helpers; the settings UI is `rikka_chat::servers` over `rikka_chat::Servers`.
- Tests run against `rikka-test-mcp`: `echo_server(folder)`, a shell script speaking stdio MCP with tools, prompts, completions, resources and templates, and `Remote`, a local streamable-HTTP server (`Answering::Json/Stream/Interrupted`, `offer(tool)`, `expire_session()`, recorded `asked()`, blocking `expect(..)`; `Remote::guarded()` adds bearer checks and the OAuth pages). The sign-in test puts a fake `rikka-open` on PATH that writes the page to a FIFO.
- Gaps: no roots, elicitation, sampling, resource subscriptions, progress tokens or client ID metadata documents.
