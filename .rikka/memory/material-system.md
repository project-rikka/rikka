- A material module defines two types named `Surface` (an `ISurface<D>`) and `Model` (an `IShadingModel` with `Data = D`), as structs or typealiases; their fields are the parameters. Built-in templates are such modules under `shaders/lib/rikka/templates/` (`rikka/standard` = OpenPBR, `rikka/skin`, `rikka/hair`, `rikka/eye`, `rikka/wireframe`, `rikka/floor`, `rikka/shadow_catcher`, `rikka/water`, `rikka/workbench`, `rikka/unlit`; see realistic-shading.md and renderer-overlay.md), user templates are Slang source that does `import rikka;`.
- Interfaces (`lib/rikka/material/{surface,model}.slang`): `ISurface<D>` has `evaluate(pixel, context) -> RikkaSurfaceData<D>` and defaults `coverage` (alpha for masked depth passes, 1) and `hull(RikkaHullVertex) -> RikkaHull` (direction, width, view depth offset; `RikkaHullVertex` carries the normal, the baked `smoothed_normal` and vertex colour; default no hull). `IShadingModel` has `prepare`, `direct(state, light, shadow)`, `indirect(state, indirect)`, `resolve`, and defaults `transmit` (per light, skipped for hulls), `resolve_hull`, `hull_scale`, `seen_through` (amount and reach for the see-through pass), `gbuffer`, `shade`. `shade` runs the generic light loop `rikka_lit`; a model may override it (graph-generated models run their own staged loops).
- Feature specialization and routing (`material/features.rs`, one mechanism for OpenPBR, graph and user templates): a parameter marked `[Feature(bit)]` (bit < 32, rikka-slang `ParameterSpec::feature`; several parameters may share a bit) turns its bit on when its resolved value is active (texture bound, bool true, number ≠ 0, enum ≠ first option); a template without any `[Feature]` gets `ALL_FEATURES`. `MaterialPool::record` stores a `Routing { features, subsurface, transmission }` per resolved record (values plus applicable overrides, beside the hook `reach`); `subsurface`/`transmission` are true when the `Role("subsurface")`/`Role("transmission")` weight is > 0. `Drawn::routing` keys buckets and shade/scatter recipes; the pipeline sets specialization constant 1 `RIKKA_FEATURES` (`PipelineKey::features`; `rikka_feature(bit)` in Slang; default all on). Gate optional code with `rikka_feature(BIT) && runtime check`. OpenPBR lobes `RIKKA_PBR_*` (coat 0, fuzz 1, thin film 2, subsurface 3, transmission 4, anisotropy 5, second lobe 6).
- Meshes may carry `MeshData::outline_normals` (object space); the renderer stores them tangent-space octahedral in `rikka.three.outline_normals` (`RikkaInstance.outline_normals`, 0 when absent) and the hull vertex rebuilds them from the deformed tangent frame. rikka-model-gpu bakes them with `Mesh::smoothed_normals` (angle-weighted face normals welded by position) for meshes with outlined toon materials.
- Vertex hook: a `Surface` that also conforms to `IVertex` (`deform(inout RikkaVertex, context, time)`; world position, normal, tangent, uv, colour) gets its own forward/depth/surfaces vertex variants (`Program::deforms`, from `spReflection_isSubType`), so prepass, masked/opaque shadows (its own shadow class), G-buffer and hull all deform alike; the surfaces variant deforms the previous position with `RikkaScene.previous_time` for motion vectors. A deforming template must declare a `[Role("displacement")] float` (else `CompileError::Unbounded` → `Error::Invalid`); its per-material value grows the draw's cull bounds (`MaterialPool::reach`, negative = never culled). Every template also has a compute `Hook` variant over the same `rikka_hooked_vertex` that the ray tracing tier uses to refit hooked draws (see the ray-tracing note); `MaterialPool::reach` decides refit or rebuild. Templates without the hook keep the shared built-in vertex shaders.
- Every interface method and implementation is `[constref]` and generic entries take `__constref` parameters, so parameters load from the block where they are used; passing blocks by value hoists every field load to entry and cost the old toon template ~30%.
- Inputs are explicit: `RikkaContext` (frame, view, instance, material record, figure head, pass flags, looked, time), `RikkaPixel` (interpolants, facing- and hull-corrected normal, view, frag coord), `RikkaLightSample` (`rikka.light`; area helpers `irradiance`/`specular`, see renderer-lighting), `RikkaShadowQuery` (`sample()` raw `RikkaShadowSample`, ray-traced visibility first where present; `map()` filtered, cached; `visibility()` adds the leading light's screen shadow; `transmittance()` tinted; `hard()` one tap; see renderer-shadows), `RikkaIndirect` (sky `irradiance`/`specular`; `occlusion` = (screen AO, screen shadow); `bend` from the occlusion image, zero for direct-pass (transparent/overlay) and hull pixels; `bent(n)` = normalize(AO·n + bend), n itself when there is no bend; `diffuse(n)` = the GI image when `bounced`, else irradiance(bent(n)) × AO; `diffuse(n, albedo, material_ao)` the same with Jimenez's multi-bounce of material_ao × AO coloured by the albedo, also on GI; `multi_bounce(albedo)`; `specular_occlusion(n, view, roughness[, material_ao])` = GTSO-style cone/cone overlap of the visibility cone (axis bent(n), cos aperture √(1 − AO)) and the lobe cone (reflect(−view, n), cos aperture 2^(−log2 10·α²)) relative to the open hemisphere's overlap, blended toward Lagarde's `rikka_specular_occlusion` below perceptual roughness 0.3, exactly 1 when unoccluded; models should light ambient with these). Free helpers in `rikka.shading`: `rikka_cap_overlap`, `rikka_cone_occlusion`, `rikka_bent_specular_occlusion`, `rikka_multi_bounce`. No module statics.
- `ISurface::transmittance(coverage, context)` (default `1 - coverage`) feeds coloured shadows through the `Tint` variant (`rikka_entry_tint`); the constref probe calls it too.
- `[Role(...)]` on a parameter tells the ray tracing tier where a template keeps its hit response (`albedo`, `albedo_texture`, `albedo_weight`, `metalness`, `metalness_texture`, `transmission`, `emission`, `emission_texture`, `emission_luminance`); the record (`material/roles.rs`) stores the offsets in `GpuMaterial`. `[Role("displacement")]` is the vertex hook's bound; `[Role("subsurface")]` and `transmission` also drive `Routing`.
- Variants: the internal crate `crates/graphics/rikka-shader-programs` is shared by the 3D shader package's build tool (`shaders/tools/programs.rs`) and the renderer. `source(module)` appends the fixed entry wrappers of `src/entries.slang` (one per `Variant`: forward, hull, depth, cutout, surfaces and surfaces_layers, their vertex variants, `tint`, `scatter`, the compute `hook`, forward_emissive and the three `*_traced` ones; `Variant::ALL`, `COUNT` and `index()` come from one macro list) plus the `rikka_entry_probe` used by the copied-method check, and a `RikkaMaterialBlock { Surface surface; Model model; }`; `compile_template` builds every variant through rikka-slang and derives the schema. `forward_emissive` also writes `IShadingModel::emitted` (default `SurfaceData.emission`) to a second HDR target and is used only while a view reads emission. `BuiltinTemplate` (id, Slang module, `ALL`, `index()`) lives there too and is re-exported by the renderer; each built-in is compiled by its own `MaterialTemplate` action into `src/programs/templates/<id>/` (17 `.spv` + `manifest.json` = schema, deforms, scatters) and listed as `shaders_3d::TEMPLATES[builtin.index()]` (`TemplateArtifact`, variants as `rikka_spirv::Shader` with build-time hash and storage-image use, so built-ins are never reflected at run time); `MaterialTemplate::prebuilt(name, &artifact)` makes a template from any such artifact (shader presets, see shader-presets). Built-in and prebuilt templates are final at creation (never drafted, optimized or reloaded) and report `Built` once their pipelines are ready. Runtime templates are built in two tiers instead (next items).
- Pipelines per pass: forward = built-in mesh VS + `forward`; hull draws (`MaterialDesc::hull()`) = `hull_vertex` + `hull`; masked prepass = `depth` (identity) or `cutout`; opaque prepass and opaque shadows stay shared built-ins; masked shadow casters get shadow classes per template (`GpuInstance.shadow_class`, `RikkaView.shadow_classes`, cull emits per class); surfaces G-buffer = `surfaces` with the model's `gbuffer` hook; subsurface pass = `scatter` (two targets) with the model's `scattered` hook. Interface hook names must not equal a parameter field name of a conforming struct: slangc segfaults instead of reporting it.
- A `Model` that also conforms to the marker `IScattering` sets `Program::scatters`; its buckets render in the screen-space subsurface pass when the drawn record routes `subsurface` (`Bucket::scatters`). Transparent buckets whose record routes `transmission` set `Bucket::refracts`.
- A variant record whose resolved routing differs from its material's own is held in `MaterialPool::warming` and draws with the material's own routing; `Renderer3dState::warm_variants` (after each `resolve`) prepares the variant's recipes for every known view in the background and `settle`s the record once all are ready, so a new override combination never compiles inline.
- `MaterialState::coverage()` (or `.alpha_to_coverage()`) draws a depth-writing cutout in the transparent phase with alpha-to-coverage; it is the strand/hair strategy for forward + MSAA.
- Blocks: the material table holds `RikkaMaterial { block, alpha_cutoff }`; `block` counts 16-byte units into the `rikka.three.material_blocks` arena whose base is `RikkaFrame.blocks`. Textures are `RikkaTexture { image, sampler }` in the block (unbound samples white). Value changes write a new block and retire the old one.
- Rust API: `MaterialTemplate::builtin(BuiltinTemplate)` / `ShaderCompiler::template(name, source)`, `template.schema()`, `template.reload(&compiler, source)`. `MaterialDesc::new(&template).preset("hair")?.with("base_color", v)?.state(..).alpha_cutoff(..)`; `set` errors are `Error::Parameter(ParameterError)`. Values change through `Renderer3d::set_material(_values)`. `desc.to_template(&other)` rebuilds a desc on another template keeping state, hull and values by name or by `Role` (how `GpuModel::restyle` switches a model material's template).
- Slang silently compiles a missing `[constref]` (copying every field at the call). `compile_template` (build time) and `draft_template` (runtime) compile the variants in one program (light-shading entries first, so the slow ones start early; block layout, schema, `Unbounded` and conformances come from that program) while a probe compiles `rikka_entry_probe` at `Optimization::None` on its own compiler beside it; it refuses (`CompileError::Copied` → `Error::Invalid`) any surviving `<Surface|Model struct>.<hook>` function whose `this` is a Function-storage pointer: `[constref]` methods are always inlined there, copied ones are not. `ShaderCompiler` skips the probe for a source it already probed.
- Runtime templates build in two tiers (`ShaderCompiler` holds three rikka-slang compilers: draft `-O0`, probe `-O0`, optimized `-O2`; effects use the optimized one). `ShaderCompiler::template`/`MaterialTemplate::reload` (and so `rikka_shader_compile::Material::{compile, reload}`) return after the draft: every variant at `-O0`, flattened by rikka-slang (`Source::flatten`), with all checks and the schema; this takes ~0.3–1.3 s, and the flattened code halves the driver's pipeline build against raw `-O0` (`-O2` itself spends 4–15 s per lit variant in spirv-opt). The draft draws exactly like the optimized build. `-O2` never runs for variants that are not drawn: `Program::shader(variant)` (the only way recipes reach a shader; `shaders()` for inspection) marks the variant demanded, and `prepare_materials` asks `MaterialTemplate::optimize` for every live program whose demand outgrows its optimized set once that generation is ready and drawn. One `rikka-shader-optimize` thread (`compiler.rs`, jobs over a channel, stale jobs skipped) compiles the demanded variants at `-O2` (`compile_variants`) and swaps in a new generation of the same revision (same schema, other variants shared), which materials adopt through the reload path; a later use (hull material, subsurface routing, a ray-traced view, emission) demands more and optimizes again. Built-ins are fully optimized from the start.
- The optimizer thread is owned by `Compilers` (`Optimizer`: sender + `JoinHandle`) and joined when they drop; queued jobs hold the `Compilers` through `Program::origin`, so they can only drop idle on a user thread or as the last job's drop on the optimizer itself, which then just ends.
- Reload: materials keep their old program and block until every pipeline of the new program (for every view and state in use) reports ready, then `MaterialPool::adopt` migrates values by name and kind (others take new defaults) and drops variants. A material's first generation that is not built yet is built inline at its first draw.
- Readiness is an event: `Renderer3dState::watch` registers `Compiling::when_ready` on each pipeline of a (template generation, recipe set) and calls `MaterialTemplate::mark_ready(program)` when the last one finishes (on the pipelines thread or the drawing thread). A template counts revisions (sources) apart from generations (programs; an optimization is a new generation of the same revision). `is_ready()`/`on_ready(notify)` mean the current revision draws (after `on_ready` the next frame draws it); `readiness()` gives `TemplateReadiness::{Pending, Drawable, Built, Failed(Arc<Error>)}`, where `Built` = the current generation is ready and every demanded variant is optimized, and `Failed` = the optimized build failed while the draft keeps drawing; `on_built(notify(Result<(), Arc<Error>>))` fires on `Built` or `Failed`. `generation()` changes on every swap, optimization included. A swapped-in optimized generation only builds its pipelines at the next draw, so on-demand hosts use `watch(notify) -> TemplateReadiness`: atomically returns the readiness and, while `Pending`/`Drawable`, calls `notify` once at the next build step (a generation drawable or ready, an optimized generation swapped in, a failure). Readiness is per template, not per renderer.
- Textures in material values, `set_material_values` and look/figure overrides go through `TexturePool::grow` (minified mip growth) before their slots are encoded.
- One schema vocabulary for materials and effects lives in rikka-slang (`ParameterKind` includes `UInt` and `Texture { kind, sampler }`); `Value` (`Float`, `Vec2–4`, `Int`, `UInt`, `Bool`, `Enum`, `Texture`) and `ParameterError` (`owner` = template or effect name) serve both.
- Overrides: `Look::overrides` (scene) then `Figure::overrides` (per figure) apply by name to every template declaring the name (`Scope::All`) or one template (`Scope::Template(id)`). `MaterialPool::resolve` (before each frame) caches the applicable list per (program generation, figure) and a variant record per (material, list hash); unused variants are retired after `VARIANT_KEEP_FRAMES`. Unchanged frames upload nothing.
- Figure looks are graph presets (figure-shading note); their class traits are parameter presets named after `ToonSurface` classes, and liquids take their art style from `Look::liquid` (renderer-fluid).
- Material records and light profiles live in GPU-mirrored tables (`src/mirror.rs` `MirroredTable<T, WIDTH>`): a host copy of fixed-width rows, a dirty range staged and copied at flush, power-of-two growth that re-uploads every row, and index reuse deferred by `retire(index, after)` until `reclaim(finished)`. `MaterialPool` keeps `GpuMaterial` rows there and its host-only `RecordInfo` (textures, routing, reach) beside them; `LightProfilePool` keeps 128 × 64 f32 rows.
