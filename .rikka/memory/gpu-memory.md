- GPU memory (`core/memory.rs`, the only file naming gpu-allocator; every other file uses its `Placement::{Device, Upload, Readback, Staging}` and opaque `Allocation`): everything is sub-allocated from gpu-allocator blocks (device 4 MiB doubling to 32 MiB, host-visible 4 MiB to 16 MiB to bound NVIDIA's host-memory free cost); only allocations the driver requires or prefers dedicated, and colour/depth attachments of 1 MiB or more (binding a compressible attachment into a shared block made NVIDIA spend ~1.6 ms in `vkBindImageMemory`), get their own `VkDeviceMemory`; allocations larger than the current block get a block of their own. The trade is fewer `vkAllocateMemory` calls for some block slack (a 2048² Paint document: 34→7 at open, 42→2 on the first stroke). `RUST_LOG=rikka_renderer::memory=debug` reports allocated vs reserved and per-kind sizes.
- Allocation ahead of need (`core/provision.rs`): `Provision::start(device, make)` creates GPU objects on the process-wide `rikka-provision` thread (holding only a weak device); `take()` never blocks, and an unclaimed result is dropped there. Frames allocate inline only when nothing was provided in time.
- Transient memory ages by wall time (`core::runtime::UNUSED_FOR`, 3 s), not frames: fx scratch targets, spare backdrops, resting scene images. Staging (`core/staging.rs`) is one belt per `FrameRing`, not aged while rendering: ≤8 chunks (≤1 MiB, appended to while in flight, rewound once their last frame completed) and dedicated power-of-two buffers for bigger uploads, spares kept within 16 MiB; taking a dedicated buffer provides another of its size on the provision thread, so the next large upload finds one. Instance uploads go through `StagingBelt::stage_gathered` (copies split and grouped per ≤1 MiB chunk), so a new scene's first upload reuses chunks instead of allocating. Only `trim()` frees them, because NVIDIA spends ~0.12 ms per MiB freeing host-visible memory and blocks queue submission meanwhile (it showed as a 3–8 ms frame 3 s after any big upload). `Renderer::trim()` drops what has aged, frees retired resources without a frame and returns idle frame and compute command-buffer memory to the driver; rikka-ui painters and the compositor call it once `TRIM_AFTER` (one second past `UNUSED_FOR`) has passed since their last frame.
- `FrameRing` creates all `MAX_FRAMES_IN_FLIGHT` (3) slots up front and always leases the oldest, so slots rotate evenly; the 3D frame-data host slots and ray scene slots are likewise created for all three at construction, so a slot first used under later GPU load never allocates in a steady frame.
