# Rikka

A high-performance Linux-only operating system built around its own Wayland compositor.

## Build rules

- Bazel owns every build, test, lint, shader and install. Run everything inside `nix develop` (or `nix develop --command bazel …`). Nix supplies the toolchain, the native libraries, the pinned assets and Bazel; `nix/bazel.nix` hands them to Bazel as the `@nix` repository (`@nix//:paths.bzl` holds every store path) and builds the remote executors' image from the same closure. Run `nix flake check --no-build` only after shell or flake changes.
- Bazel picks where builds execute from the main checkout's `.env`, shared by every worktree: before each command the dev shell's Bazel launcher runs `bazel/buildbuddy/wrapper` (through `BAZEL_WRAPPER`), which writes `.bazel/execution.bazelrc` with `--config=remote` when `.env` sets `BUILDBUDDY_API_KEY` and `--config=local` otherwise, so nobody passes an execution config by hand. With `--config=remote` actions run on BuildBuddy in the `nix/bazel.nix` image and nothing comes back unless something local needs it (`--remote_download_minimal`; `bazel run`, local tests and `xtask` fetch their own outputs), zstd-compressed, and the disk cache in `~/.cache/bazel/disk` keeps what came back for every worktree; `bazel/buildbuddy/credential-helper` sends the key, and the image on GHCR is public, so executors pull it without credentials. With a key everything runs remotely: never execute builds, tests or lints on this machine while BuildBuddy is reachable; only tests that need this machine (`--config=gpu`, `--config=machine`) run here. `.github/workflows/rbe-image.yml` pushes the image to GHCR whenever `nix/`, the flake, the toolchain or `third_party/rust/Cargo.lock` (grammar versions) changes, so after changing them push first and wait for the new image rather than building locally. Only when BuildBuddy itself is unavailable fall back to `--config=cache` (local execution, remote cache) or `--config=local` (no remote at all). Bazel's output links live under `.bazel/`.
- Every package has a `BUILD.bazel` using `rikka_library`, `rikka_proc_macro`, `rikka_binary` and `rikka_test` from `//bazel/rust:defs.bzl`; they apply edition 2024, the workspace lints, the profiles and the session RUNPATH, so never call `rust_*` rules directly. They also default the crate layout (`src/**/*.rs` with `src/lib.rs` or `src/main.rs`; for a test `tests/**/*.rs`, `tests/<name>.rs` and every other file under `tests/` as data), so a target names `srcs`, `crate_root` or `data` only when it differs. Each target lists exactly the crates its own sources name: a test does not repeat its library's `deps`, and `--config=check` rejects a dependency that is not used. Third-party crates (with version and features) are declared once in `third_party/rust/crates.MODULE.bazel` and depended on as `@crates//:<name>`; features are unified, so every crate builds once with one feature set. Specs that only hold a dependency's resolution (no target names them) are listed in that file's `_RESOLUTION_PINS`. After changing a spec or annotation, repin with `CARGO_BAZEL_REPIN=1 bazel build --nobuild //...`, which rewrites `third_party/rust/Cargo.lock` and `cargo-bazel-lock.json`.
- Libraries live only in `crates/<layer>/rikka-<name>` (app-private ones in `apps/<group>/<app>/crates/`); executables only in `apps/` (user apps) and `system/` (the compositor, shell and system services). `apps/system/` holds the apps bound to the Rikka session (Linux only); `apps/general/` holds the apps that also run on Windows. A library target is named after its folder, so `//crates/ui/rikka-ui` is the crate `rikka_ui`.
- The application SDK lives only in `sdk/`: `sdk/rikka.ridl` is the IDL and the one source of truth. It describes an object model (classes with constructors, methods, properties and view declarations, enums, flags, callbacks, errors); the C ABI is derived from it and every language is a projection of it. `sdk/codegen` (`rikka-sdk-codegen <idl> <language> <outputs…>`) parses and validates the IDL, lowers it to the C ABI and renders each language from its askama templates in `sdk/codegen/templates/<language>/`. Every language's bindings are their own package `sdk/bindings/<language>/`, declared with `rikka_bindings` from `//sdk/codegen:defs.bzl`, which generates `generated/<out>` and diff-tests it against the committed `<out>`; change the API in the IDL, then run `bazel run //xtask -- sdk`, which refreshes every output of `//sdk:bindings`. `sdk/native` implements the ABI as `librikka.so.0` (`//sdk/native:rikka`) over the Rust export layer generated at build time. C consumers depend on `//sdk/bindings/c` and C++20 consumers on the idiomatic `//sdk/bindings/cpp`. Go (cgo through pkg-config), C# (.NET 8+, source-generated P/Invoke), Java (22+, the FFM API) and Python (3.10+, ctypes) consumers depend on `//sdk/bindings/go`, `//sdk/bindings/csharp`, `//sdk/bindings/java` and `//sdk/bindings/python`; each is also a package of its ecosystem (`go.mod`, `Rikka.csproj`, `pom.xml`, `pyproject.toml`) that install ships under `share/rikka/sdk/`. A new language is a module in `sdk/codegen/src/languages/` listed in `sdk/codegen/src/language.rs`, its templates, a `sdk/bindings/<language>/` package added to `//sdk:bindings`, tests in `sdk/tests/<language>/` and every example in `sdk/examples/<language>/`. C and C++ programs use `rikka_cc_binary` and `rikka_cc_test` from `//bazel/cc:defs.bzl`, and C-ABI libraries `rikka_shared_library`, so they get the session RUNPATH. Go, C#, Java and Python code builds, runs and tests with `rikka_go_library`/`rikka_go_binary`/`rikka_go_test`, `rikka_csharp_library`/`rikka_csharp_binary`/`rikka_csharp_test`, `rikka_java_library`/`rikka_java_binary`/`rikka_java_test` and `rikka_py_library`/`rikka_py_binary`/`rikka_py_test` from `//bazel/<language>:defs.bzl`, which run the shell's Go, .NET SDK, JDK and Python from `@nix//:paths.bzl`.
- A crate with `locales/` gets `RIKKA_LOCALES` from the rules automatically. Shaders live in a `<crate>/shaders/` package declared with `rikka_shaders` from `//bazel/slang:defs.bzl`: every `.slang` file is its own action, `lib/` holds importable modules and `src/lib.rs` includes `shaders.rs`. Other generated code runs a small `rikka_binary` tool through `run_binary`. Pinned downloads (icon fonts, grammars, Gecko, Krisp) come from `nix/packages/` and `nix/dist/` through `@nix//:paths.bzl`. Built code never names a store path: programs find what an install keeps beside them (Gecko, grammars, icon fonts) through `rikka-shipped`, and the rules give development runs and tests the dev shell's copies through `RIKKA_*_PATH` (`//bazel/shipped:defs.bzl`).
- The web engine is Gecko built from source in `engine/gecko/` (MPL-2.0, its own `LICENSE`): `upstream.toml` pins a Firefox release commit, `patches/` holds one patch per Firefox file, `rikka/` is the `--enable-project=rikka` Gecko project (launcher, prefs, the `embedding/` C++ bridge, `components/` JS) and `mozconfig` configures it. Its wire types are the internal crate `//crates/web/rikka-gecko-protocol`, which only `rikka-web` uses; change both together. Gecko is too large and network-bound for Bazel actions, so `xtask gecko` drives `mach` outside Bazel in `.bazel/gecko` (`--work` moves it): `assemble` checks out the pin, applies the patches and mirrors the project, `build` and `package` build with configure-bootstrapped toolchains and the Rust channel Firefox's `linux64-rust` names (through rustup, so cross-language LTO matches), `export-patches` turns edits in `.bazel/gecko/firefox` into `patches/`, and `follow` carries the patches onto the newest Firefox release. `mach` and rustup run inside the dev shell's `rikka-gecko-build` FHS environment (`nix/gecko-build.nix`) with a whitelisted environment, so the bootstrapped toolchains run on NixOS and never see the dev shell's compilers. The `gecko` workflow builds every engine change with `--release` and attests the archives built on `main`; `gecko-follow` proposes each new Firefox release as a pull request. The dev shell and the distribution use the engine pinned by `nix/dist/gecko.json`.
- Benchmarks are outside the product build. Every target under `benchmarks/` uses `bench_library`, `bench_binary`, `bench_test` and `bench_cc_library` from `//benchmarks:defs.bzl`, which make it `testonly`, `manual` and LLVM-compiled, so `//...` never builds them. Comparator crates come from their own crate universe, `@bench_crates//:<name>`, declared in `third_party/comparators/crates.MODULE.bazel` with its own `Cargo.lock` and `cargo-bazel-lock.json` there (repin only it with `CARGO_BAZEL_REPIN=1 CARGO_BAZEL_REPIN_ONLY=bench_crates bazel build --nobuild //benchmarks:parity`); Rikka's own crates and their third-party crates stay on `@crates`. C and C++ comparators are `http_archive`s in `third_party/comparators/`. A new benchmark program joins `//benchmarks:programs`, a suite's parity test `//benchmarks:parity`.
- Usage examples exist only for the SDK, in `sdk/examples/<language>/`: one self-contained program per file (Go: per directory `<name>/main.go`), discovered by its package's `glob`, so adding the file adds `bazel run //sdk/examples/<language>:<name>`. File names follow the language (`text_editor.c`, `TextEditor.java`) and `example_name` from `//sdk/examples:defs.bzl` turns them into one snake_case target name. Every language has the same examples with the same behaviour; Python examples are also type-checked by `//sdk/examples/python:types`. Programs started by `bazel run` and tests run from the runfiles root, so they name the files they read (listed in `data`) relative to the workspace. There is no top-level `examples/`, and crates hold no `examples/`.
- A crate's tests live only in its `tests/`: `tests/main.rs` is the one test binary (`rikka_test(name = "main")`) and declares a `mod` per topic file beside it. `src/` holds no tests and no test-only code, modules, hooks or features. The SDK is tested through each binding's public API by tests in `sdk/tests/<language>/`, and the codegen through its command line in `sdk/codegen/tests/`.
- Add a test only for what a plausible change could break unnoticed: a public entry point's main path and important failures, conformance to formats, protocols and external oracles, data loss, security and permissions, solver properties, and costly regressions. Leave out constants, labels, table sizes, private helpers, UI internal state and timing, what the compiler guarantees, third-party behaviour and duplicates.
- Tests go through the public API. Never widen visibility for a test; extract the rule into its own crate instead. Program logic worth testing lives in an app-private crate under `apps/<group>/<app>/crates/`.
- Near-identical cases are one table-driven test; a regression joins its topic file. Shared helpers are `rikka-test-*` crates, `testonly` so only tests may use them. A test has 60 s (`rikka_test(limit = …)` raises it), so keep GPU and simulation tests lean.
- Every test runs in a hermetic environment and remotely unless it needs this machine. The test macros of every language make `<name>` a launcher (`hermetic_test` from `//bazel/test:defs.bzl`) around the program `<name>_bin`: it gives each test a fresh scratch home, XDG, runtime and temporary tree and no session sockets, passes `--test_arg` through, and for Rust runs each test of a shard in its own process, four at once unless the tests need this machine. `gpu = True` marks tests that need this machine's GPU and `tests/machine.rs` is `rikka_test(name = "machine", machine = True)` for a DRM render node, input devices or a sound card; plain `bazel test` skips both, `--config=gpu` and `--config=machine` run them here, one test at a time, and Bazel reruns them only when their inputs change.
- Layers are Bazel visibility: internal crates are visible only to `crates/`, `benchmarks/` and `xtask`; public crates are `//visibility:public` and also used by apps and system binaries; app-private crates only by their app. Apps and system binaries depend on public crates directly; there is no facade crate.
- Everything targets Linux except `apps/general/` and the crates they reach, which also build for Windows: `--config=windows` (`//bazel/platforms:windows`) cross-compiles them on the same executors as `x86_64-pc-windows-gnullvm` with llvm-mingw (UCRT, toolchain runtime linked statically), and `NIX["windows_runtime"]` holds the DLLs and fonts a Windows install ships. Rust code splits platforms with `#[cfg(unix)]` / `#[cfg(windows)]`, each backend in its own module behind one API; Windows APIs come only from `@crates//:windows`. BUILD files pick platform deps with `select` on `@platforms//os:linux` / `@platforms//os:windows`, and a target that is Linux-only says `target_compatible_with = ["@platforms//os:linux"]`, so `bazel build --config=windows //...` skips it and everything above it. Tests run only on Linux; Windows code is checked by building with `--config=windows --config=check`. The other target is musl, for the static installer (`//bazel/platforms:linux_musl`).

## Commands

| Task | Command |
|---|---|
| Build | `bazel build <targets>` |
| Check: build, clippy, format check and tests in one run | `bazel test --config=check <targets>` |
| GPU / machine tests | `bazel test --config=gpu <targets>` / `bazel test --config=machine <targets>` |
| Build and lint for Windows | `bazel build --config=windows --config=check <targets>` |
| Format edited files | `rustfmt --edition 2024 <files>` |
| Format the whole workspace | `bazel run @rules_rust//:rustfmt` |
| Benchmark parity tests | `bazel test //benchmarks:parity` |
| Run a benchmark | `bazel run --config=bench //benchmarks/<suite>:<program> [-- <filter>]` |
| Build every benchmark | `bazel build --config=bench //benchmarks:programs //benchmarks:parity` |
| Run the compositor and shell in a window | `bazel run //xtask -- compositor` (dev build; `--release` optimises) |
| Editor setup | `bazel run @rules_rust//tools/rust_analyzer:setup -- <vscode\|neovim\|helix\|print>` |
| Regenerate the SDK's committed bindings | `bazel run //xtask -- sdk` |
| Build the Gecko engine | `bazel run //xtask -- gecko build` (`--release` adds cross-language LTO) |
| Turn Firefox tree edits into engine patches | `bazel run //xtask -- gecko export-patches` |

- While editing, run only the narrowest command that answers the question at hand: `bazel build` of the crate you are changing until it compiles, and `bazel test <target> --test_arg=<test>` for the behaviour you are working on. Leave clippy, format checks, consumers and untouched packages to the final check.
- Format the Rust files you edited with `rustfmt --edition 2024` once you are done editing them.
- When the task is done, after the last edit, run `bazel test --config=check //...` once, plus `--config=gpu` and `--config=machine` over touched packages with such tests. After fixing a failure, rerun the same command. Later messages in the conversation rerun it only when code changed since it passed.
- After changing a public crate's API, also build its docs, which deny warnings: `bazel build //<crate>:<name>_doc`. Locale catalogs are checked against their `en.toml` when `catalogs!()` expands, so a mismatch fails the build.

## Caches

- Results are shared through BuildBuddy's cache, `~/.cache/bazel/disk` (64 GiB, least recently used first) and the repository cache of `~/.cache/bazel`; every worktree has its own output base and reuses them all.
- Never delete caches to fix a build. `bazel aquery` shows an action's inputs and command line; `bazel clean` is only for an intentional reset.

## Release

| Task | Command |
|---|---|
| Compositor | `bazel build --config=release //system/rikka-compositor` |
| Release components | `bazel run //xtask -- release components <component>… \| --all (--patch \| --minor \| --major \| --version <x.y.z>)` |
| Release every component again after nixpkgs moved | `bazel run //xtask -- release rebuild` |
| Release the installer | `bazel run //xtask -- release installer (--patch \| --minor \| --major \| --version <x.y.z>)` |
| Release the Gecko engine | `bazel run //xtask -- release gecko` |
| Portable components for a local distribution | `bazel run //xtask -- dist build <component>… --version <x.y.z> --out <dir>` |
| Merge them into a clone of the distribution | `bazel run //xtask -- dist publish --entries <dir> --into <clone>` |
| Static installer | `bazel build --config=installer //installer:rikka-installer` |

- `xtask/src/components.rs` defines every shipped component (its session and privileged contents by Bazel label, installer offer, minimum base version, PAM services) over the model in `xtask/src/shipped.rs`.
- Rikka is distributed as prebuilt binaries through the flake `github:project-rikka/packages`, which nobody edits by hand; there are no release tags or release workflows in this repository. Whoever can write to that repository releases from a clean, pushed checkout with `xtask release`: it builds the components on BuildBuddy with `--config=dist` (release, the `linux_portable` platform: no RUNPATH, the standard interpreter, no store path anywhere), verifies them with Nix, uploads the archives to the `binaries` release of `project-rikka/packages`, commits `nix/dist/`, `release.json` (versions, builds, source revisions) and this repository's nixpkgs pin there, and deletes archives the last 10 releases no longer name. When this repository's nixpkgs pin moved, a release rebuilds every published component as the next build of its version. The installer goes to the same release as `rikka-installer-x86_64-linux`, which `installer/install.sh` downloads.
- `xtask release gecko` takes the engine the `gecko` workflow built and attested on `main` for HEAD's `engine/gecko`, uploads it to the `binaries` release, writes `nix/dist/gecko.json` (commit it) and publishes the pin to `project-rikka/packages` at once, unless the protocol changed since a published component linking Gecko was built; then those components ship it with their next `release components`. Pruning keeps every engine the last 10 releases or the checkout pin.
- Development runs go through `xtask app` and `xtask compositor`. To run a local build at login, `dist publish` it into a clone of the distribution and rebuild with `--override-input rikka path:<clone>`.
- Profiles live in `.bazelrc` and `//bazel/rust:defs.bzl`. Development builds compile workspace crates with Cranelift at opt-level 1 with line tables and debug assertions, third-party crates and build tools with LLVM at opt-level 2 without debug info, link with mold and pipeline metadata. Release builds (`--config=release`) use opt-level 3, fat LTO, one codegen unit, panic abort and stripped symbols. The installer build uses musl, `opt-level = "z"`, fat LTO and unwinding.
